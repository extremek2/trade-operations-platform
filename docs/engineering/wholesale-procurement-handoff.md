## 완료된 범위

다음 네 커밋이 하나의 도매 카탈로그·국내 매입 수직 흐름을 구성한다.

| 커밋 | 완료 내용 |
|---|---|
| `9c61174` | 도매꾹 고정 샘플 및 라이브 조회 어댑터, API 원본 제안 초안, 국내 매입 PO·외부 주문 기록·선적 없는 입고 |
| `c7dcb78` | 서버의 라이브 API 키 설정 여부 노출과 화면의 라이브 모드 비활성화 |
| `3eb6189` | 수량 구간가 보존 및 희망 수량에 맞는 견적 단가 적용 |
| `f445d89` | PO에 API 원본 상품을 추적하고 승인·외부 주문 전에 가격/재고 재확인 강제 |

현재 샘플 흐름은 다음 순서로 연결된다.

```text
도매꾹 검색/상세
  → API 원본·해시·조회 시각을 가진 제안 검토 초안
  → 행 확인 및 희망 수량 선택
  → 수량 구간가가 적용된 공급 견적
  → 예상 원가
  → 국내 재고 매입 PO
  → 가격·재고 재확인
  → 내부 승인
  → 사용자가 원 사이트에서 주문 후 주문번호·금액 기록
  → 선적 없는 국내 입고와 재고 로트
```

중요한 통제는 다음과 같다.

- API 원본 상품 ID는 사용자가 수정할 수 있는 공급사 SKU와 별도로 보존한다.
- PO 행은 플랫폼, 원본 상품 ID, 원본 URL, 최초 조회 시각을 스냅샷으로 가진다.
- API 출처 국내 PO는 가격·재고 재확인을 통과하기 전 승인할 수 없다.
- 재확인 결과가 `CHANGED` 또는 `FAILED`이면 기존 승인을 초안으로 되돌린다.
- 외부 주문 기록에는 30분 이내의 `PASSED` 결과가 필요하다.
- 샘플 판매자로 만든 PO는 실제 외부 주문과 입고로 전환할 수 없다.
- 실제 주문 생성 API, 결제, 이메일 발송은 수행하지 않는다.

## 데이터와 API 기준

- Flyway `V15`: 도매 카탈로그 API 원본
- Flyway `V16`: 국내 매입 인계와 선적 없는 입고
- Flyway `V17`: 제안 행의 수량 구간가
- Flyway `V18`: PO 카탈로그 출처와 가격·재고 재확인 상태
- 상태 조회: `GET /api/v1/wholesale-catalog/status`
- 상품 검색: `GET /api/v1/wholesale-catalog/items?keyword=...&mode=SAMPLE|LIVE`
- 상품 상세: `GET /api/v1/wholesale-catalog/items/{itemId}?mode=SAMPLE|LIVE`
- 제안 초안 생성: `POST /api/v1/wholesale-catalog/items/{itemId}/offer-draft?mode=...`
- PO 재확인: `POST /api/v1/trade-cycles/purchase-orders/{orderId}/catalog-recheck`

- 백엔드 전체 회귀: 138개 중 실패 0, skip 1. 이후 추가한 승인 무효화 도메인 테스트는 단독 통과했다.
- 샘플 통합 테스트는 검색·상세·원본 제안·구간가 견적·PO 생성·승인 차단·재확인 통과·승인을 한 흐름으로 확인한다.
- 프런트 전체: 13 suites, 66 tests 통과.
- 프런트 프로덕션 빌드: 성공. `caniuse-lite` 데이터가 오래됐다는 비차단 경고만 있다.
- 중단 시점 작업 트리: 깨끗함.

## 아직 입증하지 않은 것

현재 환경에는 `DOMEGGOOK_API_KEY`가 설정되지 않았다. 따라서 아래 항목은 구현 여부와 별개로 실제 검증을 주장하지 않는다.

- 라이브 XML 응답이 현재 파서 계약과 일치하는지
- 사업자 전용 가격, MOQ, 구간가, 재고, 배송비가 사이트 화면과 일치하는지
- 가격 변경·품절·API 한도/오류가 실제 응답에서도 예상 상태로 전환되는지
- 실제 사업자 계정으로 해당 상품을 구매할 수 있는지
- 주문·결제·부분 입고·취소·반품 증빙이 실제 운영에 충분한지

## 다음 재개 순서

1. 도매꾹 API 키를 채팅이나 프런트 코드에 남기지 말고 서버 환경변수 `DOMEGGOOK_API_KEY`로 설정한다.
2. `/api/v1/wholesale-catalog/status`의 `liveConfigured=true`를 확인한다.
3. 실제 주문 API는 호출하지 않고 검색·상세 20~30건을 읽기 전용으로 조회한다. 상품번호, 판매자, 사업자 전용 여부, MOQ, 고정가/구간가, 재고, 배송비, 상품 URL을 원 사이트 화면과 대조한다.
4. 표본 결과를 익명화한 회귀 fixture와 필드별 일치표로 남긴다. 불일치·누락 필드는 자동 확정하지 않고 사용자 확인 상태로 보낸다.
5. 가격 변경과 품절 표본으로 PO의 `CHANGED`/`FAILED` 및 승인 해제를 확인한다.
6. 라이브 실증 후 P1으로 옵션·배송비 구조화와 국내 매입 원가 입력 간소화를 진행한다.
7. 사업자 구매 자격이 확인되면 실제 상품 한 건을 사용자가 직접 주문하고 주문번호·실결제액·부분 입고·취소/반품 증빙을 검증한다.

API 키가 계속 없으면 6번의 옵션·배송비 모델과 국내 원가 화면 개선부터 진행할 수 있지만, 라이브 호환성이 확인된 것으로 기록해서는 안 된다.
