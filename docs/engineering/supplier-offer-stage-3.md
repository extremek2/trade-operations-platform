## 구현 내용

V9은 `purchase_order` 머리의 단일 원가 시나리오 연결을 각 `purchase_order_line`으로 이전한다.
기존 행은 V9 적용 중 원래 원가 시나리오로 순방향 이관되며, 이후 한 원가 시나리오는 한 발주 행에만
연결할 수 있다. 같은 조직과 같은 공급 견적에서 만든 서로 다른 상품의 완성 원가안만 한 발주로
묶는다. 선택 상태가 아닌 견적, 중복 원가안, 이미 발주된 원가안과 서로 다른 견적의 혼합은 거절한다.

발주 예상 원가는 행별 원가 시나리오의 총 도착원가 합계로 보존한다. 발주 행의 수량은 해당 원가안의
주문수량을 사용하므로 공급처 MOQ와 구매 선택 희망수량을 발주수량으로 직접 오인하지 않는다.
화면은 같은 견적의 최신·미발주 원가안만 함께 선택할 수 있고, 선적 배정 시 실제 발주 품목을 고른다.
입고 화면도 선적 배정의 상품명을 표시한다.

재발주 판단은 더 이상 발주의 첫 상품을 암묵적으로 사용하지 않는다. 사용자가 해당 발주에 속한
상품을 명시하며 API는 다른 상품 참조를 차단한다.

## 검증과 남은 작업

PostgreSQL 통합 테스트는 같은 견적의 원가안 두 개로 한 발주를 만들고, 품목별 선적 배정과 다행
입고, 로트 생성, 실제 원가 마감까지 진행한다. 원가안 재사용과 서로 다른 견적 혼합도 차단한다.
기존 단일 품목 API 흐름과 조직 격리·낙관적 잠금도 유지한다.

현재 실제 비용은 입고수량 비율로 로트에 배부한다. 무게·부피·금액·수동 기준 배부는 실제 사례를
확보한 뒤 별도 정책으로 추가한다. 실제 파일 바이너리 저장, Excel/CSV·텍스트 PDF 파서, OCR,
이메일과 외부 공급처 API도 아직 구현하지 않았다. 다음 시작점은 Excel/CSV 결정론적 파서와 파일
해시 기반 멱등 재업로드다.
