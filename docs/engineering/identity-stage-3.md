# 3단계: 가입 승인 화면과 인증 통합

> 역사 기록: 이 문서의 migration 번호와 테스트 수치는 작성 당시 기준이다. 현재 기준선은 ADR-0002를 따른다.

- 작성일: 2026-09-08
- 상태: 구현·검증 완료
- 기준: [단계별 설계](../product/identity-access-approval-design-v1.md)
- 이전 단계: [가입 승인 백엔드](identity-stage-2.md)

## 구현 범위

| 경로 | 대상과 동작 |
|---|---|
| `/` | 화주 로그인·회원가입. 신규 가입 후 신청 상태로 이동 |
| `/application` | 본인 신청 상태·이력, 확인 메일 재발급, 반려 사유와 보완 재신청, 승인 후 작업 공간 진입 |
| `/verify-email` | 이메일 링크 확인. 사용자가 확인 버튼을 눌러야 토큰 소비 |
| `/system-admin/login` | 시스템관리자 전용 로그인 |
| `/system-admin/applications` | 상태별 신청 목록·페이지 이동 |
| `/system-admin/applications/:id` | 신청 상세, 승인·반려와 처리 이력 |

ACCOUNT 세션은 조직 업무 화면에 진입하지 않는다. PLATFORM 세션은 관리자 화면으로
이동하고, 승인된 신청자는 조직 컨텍스트로 전환한 후 기존 화주 작업 공간에 진입한다.
일반 사용자가 관리자 주소로 접근하면 관리자 API를 조회하지 않고 접근 불가 화면을 표시한다.
서버 권한 검증도 유지하므로 주소 변경이나 API 직접 호출로 우회할 수 없다.

반려 재신청은 이전 신청 ID를 연결하고 이전 이력을 보존한다. 관리자 화면은 신청자에게
공개할 반려 사유와 내부 메모를 구분하며, 최종 확인에 대상 이메일을 표시한다.
중복 클릭은 차단하고 이미 처리된 신청의 409 응답은 최신 상태를 다시 조회한다.
처리 결과를 확신할 수 없는 통신 실패에서는 상세를 다시 조회한 후 재시도하게 한다.

## 인증과 링크 처리

- 액세스 토큰은 메모리에만 보관하고 기존 HttpOnly refresh 쿠키로 세션을 복원한다.
- 동시 refresh는 한 요청으로 합친다. Web Locks 지원 브라우저에서는 탭 간 세션 변경도 직렬화한다.
  미지원 브라우저는 같은 탭 안의 중복 refresh 방지만 제공한다.
- 복원 중 통신 오류·503은 로그아웃으로 처리하지 않고 복구 화면을 제공한다.
  로그아웃·사용자 전환 전에 시작한 프로필 응답은 세션 버전으로 무시한다.
- 이메일 확인 토큰은 URL fragment에서 읽은 뒤 주소에서 제거하고 브라우저 저장소에 기록하지 않는다.
  확인 요청에는 로그인 쿠키와 Authorization 헤더를 보내지 않는다.
  확인 전에 새로고침하면 이메일 링크를 다시 열어야 한다.
- 메일 재발급은 화면에서 60초 재요청을 제한하고 서버의 요청 제한도 유지한다.
- 모바일 배치, 상태·오류 안내, 키보드 포커스 표시를 추가했다.

## 검증

- 프런트엔드 테스트 16개 통과: 상태별 접근, 확인 링크, 복원 실패와 재시도,
  메일 요청 제한, 재신청, 중복 결정과 409, refresh 처리 등.
- 프런트엔드 프로덕션 빌드 성공.
- PostgreSQL 기반 백엔드 전체 테스트 49개 통과, bootJar 빌드 성공.
- 실제 브라우저 E2E 2개 통과: 가입→이메일 확인→승인→조직 업무 접근,
  반려→사유 확인→보완 재신청. 미승인 API 접근 차단, 관리자 접근 차단,
  내부 메모 비공개와 확인 링크 재사용 차단도 검증한다.
- 관리자 승인 화면과 모바일 반려 화면을 캡처해 확인했다.
- 테스트 전용 서버 클래스가 운영 bootJar에 포함되지 않음을 확인했다.

## 실행 방법

프런트엔드 폴더에서 실행한다.

```bash
npm ci
CI=true npm test -- --watchAll=false --runInBand
npm run build
npm run test:e2e
```

E2E에는 JDK 17, Node.js 20 이상, Docker와 Google Chrome이 필요하다.
Playwright가 프런트엔드 3000번 포트와 테스트 API 18080번 포트를 직접 시작하므로
두 포트는 비어 있어야 한다. 기존 서버를 재사용하지 않는다.
필요하면 `GRADLE_USER_HOME=/tmp/trade-ops-gradle npm run test:e2e`로 Gradle 캐시 위치를 지정한다.

`onboardingE2eServer` Gradle 작업은 테스트 클래스 경로에서만 실행된다.
일회용 PostgreSQL과 테스트 관리자 `admin@example.test`를 만들고, 메일은 메모리에만 보관한다.
테스트용 메일 조회 경로 `/_e2e/mail`은 전용 프로필과 테스트 서버에서만 제공된다.
테스트 비밀번호·암호화 키는 운영용이 아니다. 화면 캡처는 Git에서 제외된
`frontend/test-results/`에 생성된다.

## 운영 적용과 다음 단계

실제 운영 DB 변경, 운영 관리자 생성, 외부 메일 발송과 배포는 수행하지 않았다.
실제 가입·결정에는 MAIL_OUTBOX_KEY 설정이 필요하며, 이메일 수신에는 메일 발송 설정도
필요하다. [2단계 설정 안내](identity-stage-2.md)와
[1단계 관리자 초기화 절차](identity-stage-1.md)를 참고한다.

후속 [4단계 조직 직원 권한 관리](identity-stage-4.md)에서 OWNER의 ADMIN 지정·해제와
제한된 직원 관리를 구현했다. 포워더·관세사의 건별 이메일 초대는 5단계 승인 후 구현한다.
