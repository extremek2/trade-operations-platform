## 정책과 구현 범위

조직 업무 화면에 `/organization/members` 직원 관리 페이지를 추가했다.
현재 선택된 조직의 OWNER·ADMIN만 직원 목록과 관리 기능을 이용할 수 있다.
시스템관리자의 PLATFORM 세션에는 직원 관리 권한이 자동 부여되지 않는다.

| 행위자 | 직원 추가·변경 범위 |
|---|---|
| OWNER | ADMIN·OPERATOR·VIEWER 추가, 역할 변경, 활성·비활성 전환 |
| ADMIN | OPERATOR·VIEWER 추가, 역할 변경, 활성·비활성 전환 |
| OPERATOR·VIEWER | 직원 관리 불가 |

본인 권한 변경과 OWNER 추가·변경·비활성화는 모두 금지한다. 따라서 일반 직원 관리
API로 마지막 OWNER를 없애거나 소유권을 이전할 수 없다. ADMIN은 다른 ADMIN을
비활성화하거나 하위 역할로 바꾸는 것도 불가능하다.

이번 단계의 직원 등록은 가입·이메일 확인을 완료한 활성 계정을 이메일로 추가하는 방식이다.
직원 전용 신규 가입·메일 초대 링크는 포함하지 않는다. 현재 공개 회원가입은 조직 개설 신청을
함께 생성하므로, 직원으로 등록된 계정의 미처리 신청은 이력에 남는다. 직원 등록 후 해당
신청을 승인하여 다른 조직 OWNER를 중복 생성하는 동작은 409로 차단한다. 필요하면
시스템관리자가 직원 등록 사실을 확인하고 해당 신청을 반려할 수 있다.

현 로그인 화면에는 조직 선택 기능이 없어 신규 직원 등록·재활성화 시 다른 활성 조직 소속은
허용하지 않는다. 기존 다중 소속 데이터를 삭제하거나 변경하지는 않는다. 다중 조직 선택과
직원 전용 가입·초대는 후속 확장 대상이다. 신규 조직 개설 승인도 현재 활성 소속이 있으면
차단하며, 직원 등록과 승인 모두 같은 사용자 행을 잠가 동시 처리 시 중복 소속을 방지한다.

이 페이지는 화주 조직 내부 직원용이다. 포워더·관세사 연락처와 건별 접근 권한은 5단계
외부 참여 모델에서 처리한다. 외부 업체별 최대 3명 제한을 내부 직원 수에 적용하지 않는다.

## API

선택된 조직은 서버의 인증 컨텍스트에서 결정한다. 요청으로 조직 ID나 OWNER 역할을
지정하여 권한을 우회할 수 없다.

| 메서드·경로 | 요청·응답 |
|---|---|
| `GET /api/v1/organizations/current/members` | `page`, `size`로 활성·비활성 직원 목록 조회. 최대 페이지 크기 100 |
| `POST /api/v1/organizations/current/members` | `email`, `role`, `reason`. 성공 시 201 |
| `PATCH /api/v1/organizations/current/members/{userId}` | `role`, `status`, `version`, `reason` |

응답은 직원의 공개 사용자 ID, 이름, 이메일, 역할, 상태, 버전, 최초 등록 시각을 제공한다.
사유는 필수이며 최대 500자다. 다른 조직의 사용자를 변경 대상으로 보내면 404,
권한 위반은 403, 중복 등록·버전 충돌은 409로 응답한다.

화면은 대상 이메일·권한·상태·사유를 최종 확인한 후 저장하고 중복 클릭을 차단한다.
실패하거나 409가 발생하면 편집을 닫고 최신 목록을 조회한 후 다시 선택하게 한다.
ADMIN 권한이 회수되어 403을 받으면 프로필도 갱신해 관리 화면 접근을 해제한다.
추가된 직원은 다시 로그인하면 조직 작업 공간으로 진입할 수 있다.

## 동시 변경·감사·세션

- 조직 행 잠금 안에서 변경을 직렬화하며, 잠금 대기 전에 읽힌 행위자 권한은 다시 읽는다.
- V16 마이그레이션으로 `organization_member.version`을 추가한다. 기존 행은 0부터 시작한다.
  변경 요청의 버전을 검사하고 JPA 버전 관리도 적용한다. 과거 V01~V15는 수정하지 않는다.
- 등록·변경은 `identity_audit_event`에 행위자, 조직, 대상 소속 ID, 변경 전후 역할·상태,
  사유와 시각을 같은 트랜잭션으로 기록한다. 물리 삭제 대신 비활성화하므로 소속 이력도 유지한다.
- 역할 변경은 기존 세션을 유지하되 보호 요청마다 최신 DB 역할로 허용 여부를 판단한다.
- 비활성화는 해당 사용자·조직의 세션을 철회한다. 재활성화해도 예전 토큰은 복구되지 않는다.
- 감사 저장에 실패하면 소속 변경과 세션 철회도 함께 롤백된다.

## 검증 결과

- 백엔드 전체 테스트 63개 통과: 직원 관리 테스트 13개와 기존 신청자 직원 등록 후 승인
  차단 테스트 1개 추가. 조직 격리, 역할 제한, 동시 요청, 버전 충돌, 세션 철회와 감사 실패 롤백 포함.
- 프런트엔드 테스트 22개 통과: OWNER·ADMIN 선택지, VIEWER 접근 차단,
  최종 확인·중복 클릭, 이메일 등록, 409 이후 최신 조회 검증.
- 실제 Chrome E2E 3개 통과: 기존 가입 승인·반려 흐름 2개와
  직원 등록→ADMIN 지정·해제→비활성화·접근 차단 1개.
- 프런트엔드 프로덕션 빌드와 백엔드 bootJar 빌드 성공.
- 모바일 직원 관리 화면 캡처와 가로 넘침 검증. `git diff --check` 통과.

실행 명령은 `api-server`에서 `./gradlew test bootJar --no-daemon`, `frontend`에서
`CI=true npm test -- --watchAll=false --runInBand`, `CI=true npm run build`, `npm run test:e2e`다.
Docker·Chrome 등 테스트 환경과 격리 방식은 [3단계 실행 안내](identity-stage-3.md)를 따른다.

## 운영 적용과 다음 단계

실제 서비스 DB 마이그레이션, 실제 직원·관리자 등록, 메일 발송과 배포는 수행하지 않았다.
V16은 테스트용 PostgreSQL에서 검증하며 운영 적용은 별도 승인 대상이다.

후속 [5단계 외부 참여](identity-stage-5.md)에서 업체별 최대 3명 담당자 초대,
건별 참여·철회, 이메일 인증과 초대 만료를 구현했다.
