## 1. 목적과 범위

회원가입 직후 조직과 OWNER 권한이 생성되는 현재 동작을 변경한다. 신청자는
이메일을 확인하고 조직 개설을 신청하며, 시스템관리자가 승인한 후 조직 업무에 접근한다.
승인은 화면과 서버 API로 처리하며 가입 건마다 수동 SQL을 실행하지 않는다.

화주 OWNER는 내부 ADMIN을 지정한다. OWNER와 ADMIN은 업체 연락처를 관리하고
포워더·관세사의 담당자 이메일을 개별 건에 초대한다. 외부 참여자를 화주 직원으로
등록하지 않으며 이메일 링크로 인증된 사용자와 건별 참여 권한을 연결한다.

초기에는 포워더·관세사의 전체 업무 통합 관리, 시스템관리자의 거래 내용 열람,
자동 OWNER 이관, PI·CI 도메인 전체 구현을 포함하지 않는다.

### 1.1 사용자와 합의한 방향

- 최초 주요 사용자는 화주다.
- 시스템관리자 전용 페이지에서 최초 OWNER 부여를 승인한다.
- 시스템 권한, 조직 소속 권한, 건별 외부 참여 권한을 분리한다.
- 외부 담당자는 이메일 링크로 자신이 초대받은 건에 접속한다.
- 화주 관리자가 업체별 소수의 담당자 이메일을 관리한다.
- 구현은 단계별 승인 후 진행한다.

### 1.2 구현 시 적용할 제안 기본값

아래는 세부 설계 제안이며 운영 실측이나 이미 확정된 정책이 아니다.

- 승인 시 조직을 최초 생성한다. 대기·반려는 조직 상태가 아닌 신청 상태로 관리한다.
- 기존 활성 조직과 OWNER는 유지한다. 기존 데이터의 재승인은 별도 작업이다.
- 최초 OWNER는 조직별 1명으로 시작한다. 일반 권한 변경 API로 OWNER를 추가하거나 제거하지 않는다.
- 외부 담당자 제한은 건별·업체별 초대 대기와 활성 참여 합계 최대 3명으로 한다.
- 외부 참여의 첫 구현 대상은 기존 shipment_case다. 거래 단위 권한은 PI 도메인 설계 시 확장한다.
- 접속용 인증 토큰은 15분, 초대 자체의 수락 기한은 7일을 기본값으로 제안한다.
  둘을 별도로 저장하고 설정으로 변경할 수 있게 한다.
- 기존 로그인 암호 방식은 화주와 시스템관리자에 유지하고 외부 참여자는 이메일 인증을 사용한다.

새 승인 절차를 우회하는 경로로 재사용되지 않도록 호출부와 테스트도 정리한다.

## 3. 권한 모델

| 주체 | 허용 | 자동으로 부여되지 않는 권한 |
|---|---|---|
| SYSTEM_ADMIN | 개설 신청 검토·승인·반려, 조직 운영 상태 관리 | 화주 거래·첨부파일 열람, 화주 직원 소속 |
| OWNER | 자기 조직 직원 관리, ADMIN 지정·해제, 외부 초대 관리 | 다른 조직 및 시스템관리자 기능 |
| ADMIN | 자기 조직 OPERATOR·VIEWER 관리, 외부 초대·철회 | OWNER·ADMIN 승격, 소유권 변경 |
| OPERATOR | 자기 조직에서 허용된 업무 처리 | 조직 권한 관리·외부 초대 관리 |
| VIEWER | 허용 범위 조회 | 변경·승인 |
| 외부 참여자 | 참여한 건에서 허용된 업무 | 화주 조직 소속, 다른 건, 재초대·권한 부여 |
| 승인 대기 신청자 | 본인 신청 조회·이메일 확인·허용된 재신청 | 신규 신청 조직의 업무 접근 |

외부 담당자의 최종 승인 등 세부 업무 권한은 해당 업무 구현 전에 권한표로 확정한다.
초기 VIEWER와 CONTRIBUTOR는 건별 조회 및 허용된 운송 문서번호 등록부터 연결한다.
기존 EDITOR라는 이름만으로 화물 전체 수정·보관·통관 승인을 허용하지 않는다.

JWT의 역할은 화면 표시 등의 힌트다. 보호된 요청마다 사용자 활성 상태, 세션 유효성,
조직 상태 및 현재 소속·참여 권한을 서버에서 확인한다. 역할 회수·조직 정지·참여 철회가
이미 발급된 토큰의 만료까지 지연되지 않도록 한다. 파일 다운로드와 목록 조회도 동일하다.

## 4. 데이터 모델

### 4.1 사용자와 신청

- app_user: 공통 사용자 ID를 유지하고 email_verified_at을 추가한다.
  이메일 표준화는 trim 및 일관된 대소문자 정책을 적용하되 +주소·점 제거 등은 하지 않는다.
  기존 대소문자 중복을 조사한 뒤 표준화 이메일의 DB 유일성을 보장한다.
- organization_application: public_id, applicant_user_id, 제출 회사 정보 스냅샷,
  상태, version, 제출·처리 시각, 승인 조직 ID, 이전 반려 신청 ID를 저장한다.
- 신청 상태: PENDING_EMAIL → PENDING_REVIEW → APPROVED 또는 REJECTED.
  이메일이 이미 확인된 사용자는 PENDING_REVIEW부터 시작한다.
- 이메일 확인 후에만 검토 대상으로 전환한다. 확인 전에는 본인 신청과 이메일 확인 API만 허용한다.
- 반려 사유와 제출본을 보존하고 재신청은 새 신청으로 생성한다. 반려 신청을 덮어쓰지 않는다.
- 동일 사용자에 대한 미처리 최초 개설 신청은 하나만 허용하고 DB 제약으로 동시 신청을 막는다.
  회사명 일치만으로 기존 회사 소유권을 인정하지 않는다.
- 기존 계정의 조직 신청은 로그인 후 별도 API를 사용한다. 같은 이메일로 계정을 중복 생성하지 않는다.

### 4.2 시스템 역할과 감사

- platform_role_assignment: user_id, role(SYSTEM_ADMIN), 상태, 부여자·부여 시각·철회 시각.
  organization_member의 역할 enum에 SYSTEM_ADMIN을 추가하지 않는다.
- identity_audit_event: actor_user_id(초기화 작업은 null 허용), actor_type,
  action, 대상 종류·ID, organization_id(nullable), 변경 전후 정보, 사유, 시각, request_id.
- 승인·반려, 역할 변경, 조직 정지, 초대·철회, 초기 관리자 설정을 기록한다.
  비밀번호와 인증 토큰은 기록하지 않는다. 승인 이력은 업무 변경과 같은 트랜잭션에서 저장한다.
- 관리자 반려 사유의 신청자 공개 내용과 운영자 내부 메모를 구분한다.

### 4.3 인증 세션과 이메일 토큰

- refresh_session에 session_kind(ACCOUNT / ORGANIZATION / PLATFORM / CASE)를 추가한다.
  organization_id는 조건부 필수로 바꾸고 CASE 세션에는 participant_id를 연결한다.
- ACCOUNT는 본인 프로필·신청·컨텍스트 선택만 허용한다. PLATFORM은 활성 시스템 역할,
  ORGANIZATION은 활성 조직 소속, CASE는 활성 건별 참여가 있어야 발급한다.
- Access Token에 session_id를 포함하고 서버가 살아 있는 세션인지 확인한다.
  갱신 시에도 동일한 현재 권한을 확인하며 refresh 토큰 회전은 원자적으로 처리한다.
- 컨텍스트 전환 시 서버 검사를 거쳐 토큰을 새로 발급한다. 클라이언트가 보낸 role을 신뢰하지 않는다.
- 외부 인증 링크에 담는 고엔트로피 난수는 해시만 DB에 저장한다.
  email_auth_token에 용도, 대상 이메일, 사용자/초대 참조, 만료·소비·철회 시각을 둔다.
- 소비는 미사용·미만료 조건의 원자적 갱신으로 처리한다. 재발송 시 이전 접속 토큰을 무효화한다.
- 링크 GET은 안내 화면만 열고 POST로 확인·소비한다. 인증 후 토큰 없는 주소로 이동한다.
- HTTPS, HttpOnly·Secure 쿠키, 쿠키 사용 변경 요청의 CSRF 방어, 발송·검증 횟수 제한을 적용한다.
  토큰을 URL 로그·분석 도구·Referer에 남기지 않고 복귀 주소는 허용된 경로로 제한한다.

### 4.4 업체와 외부 참여

- partner_company: 화주 조직이 관리하는 업체 ID·이름·유형·상태를 둔다.
  향후 실제 업체 조직과 연결할 수 있지만 연결만으로 기존 건의 권한이 확대되지는 않는다.
- external_contact를 partner_company와 연결한다. 업체 연락처 등록은 접근 권한 부여가 아니다.
- case_partner: shipment_case_id + partner_company_id로 해당 건의 참여 업체를 식별한다.
- case_participant: case_partner_id, 연락처 참조, verified_user_id, 참여 역할·접근 수준·상태.
  연락처와 검증 사용자를 함께 보존할 수 있도록 기존 user_id/external_contact_id XOR 제약을 재설계한다.
  사용자 이름 변경·연락처 교체와 별개로 행위자 ID 및 당시 식별 정보를 감사에 보존한다.
- case_invitation: 대상 이메일·초대 기한·수락·철회 이력을 보존한다.
  장기 초대 자체와 짧은 접속용 email_auth_token은 별도로 관리한다.
- 동일 사용자·동일 건의 중복 참여는 금지한다. 재초대는 기존 철회 이력을 보존하면서 처리한다.
- 3명 제한은 case_partner 행 잠금 아래 초대 대기·활성 인원을 계산하여 검사한다.
  UI 검사만 사용하지 않는다. 만료 초대는 같은 트랜잭션에서 상태 정리 후 계산한다.
- 기존 연락처의 company_name만으로 서로 다른 업체를 자동 병합하지 않는다.
  기존 데이터 매핑과 중복 처리 내역을 검토한 후 제약을 적용한다.
- shipment 권한이 연결된 다른 거래로 전파되지 않는다. 미래 trade_case 권한은 명시적 FK와
  별도 정책으로 확장하며, 무제약 target_type/target_id로 참조 무결성을 대체하지 않는다.

## 5. 승인 처리와 화면/API 계약

### 5.1 승인 트랜잭션

1. 활성 시스템관리자·세션을 확인하고 신청 행을 잠근다.
2. PENDING_REVIEW, 확인된 이메일, 활성 신청자, 요청 version을 확인한다.
3. 검토된 신청으로 조직과 최초 OWNER 소속을 생성한다.
4. 신청을 APPROVED로 바꾸고 생성 조직·승인자·승인 시각을 연결한다.
5. 감사 이벤트와 발송 대기 이벤트를 저장한 뒤 커밋한다.

동일 신청의 중복 승인·승인과 반려의 경쟁은 하나만 성공하고 나머지는 409를 반환한다.
실패 시 조직·소속·신청 변경·감사 모두 롤백한다. 이메일 실패로 승인을 되돌리지 않는다.
승인 알림에는 로그인 안내를 넣고 세션 토큰은 넣지 않는다. 신청자는 승인 뒤 조직 컨텍스트를
선택해 권한이 재검증된 세션을 발급받는다.

### 5.2 현재 구현 화면

| 경로 | 사용자 경험 |
|---|---|
| / | 화주 로그인·회원가입 탭. 신규 가입 후 신청 상태 화면으로 이동 |
| /application | 이메일 확인 안내, 본인 신청 상태·반려 사유·재신청 |
| /verify-email | 이메일 링크 확인. 명시적인 확인 버튼으로 토큰 소비 |
| /system-admin/login | 시스템관리자 로그인 |
| /system-admin/applications | 대기 신청 목록·필터·페이지네이션 |
| /system-admin/applications/:id | 제출 정보, 승인·반려, 처리 이력 |
| /organization/members | OWNER·ADMIN의 직원 권한 관리 |
| /shipments/:id | 화주 관리자의 업체 연결, 담당자 초대·상태 확인·철회 |
| /external-access | 이메일 접속 링크 확인·재요청 |
| /external-case | CASE 세션으로 초대받은 건 조회·허용된 문서번호 등록 |

이메일 발송 제공자나 내부 토큰 구조는 제품 화면에 노출하지 않는다.
시스템관리자 화면을 숨기는 것과 별개로 API가 매번 시스템 역할을 검사한다.

### 5.3 현재 구현 API

기존 `/api/v1` prefix와 응답 envelope를 유지한다. 아래 경로는 1~5단계 구현과 검증에 반영된 현재 계약이다. 후속 변경은 해당 단계의 구현 문서와 컨트롤러를 함께 갱신한다.

| API | 접근·동작 |
|---|---|
| POST /auth/signup | 계정·신청 생성, 제한된 ACCOUNT 세션과 다음 화면 반환 |
| POST /auth/email-verifications/request, /confirm | 이메일 확인 요청·소비 |
| GET /me/applications | 본인 신청만 조회 |
| POST /organization-applications | 로그인 사용자의 신규/반려 후 신청 |
| POST /auth/context | 현재 권한 검증 후 ACCOUNT·ORGANIZATION·PLATFORM 컨텍스트 선택. CASE는 이메일 링크로만 발급 |
| GET /system-admin/applications, /{id} | 시스템관리자 검토 목록·상세 |
| POST /system-admin/applications/{id}/approve, /reject | version과 처리 사유를 포함한 결정 |
| GET/POST /organizations/current/members | 현재 조직의 직원 목록·추가 |
| PATCH /organizations/current/members/{userId} | OWNER·ADMIN의 허용 범위 내 역할·상태 변경 |
| GET/POST /organizations/current/partners | 현재 조직의 외부 업체 목록·등록 |
| GET/POST /shipments/{shipmentId}/partners | 건별 업체 목록·연결 |
| POST /shipments/{shipmentId}/partners/{partnerId}/invitations | 업체 담당자 초대 |
| POST /shipments/{shipmentId}/participants/{participantId}/revoke | 건별 참여 철회 |
| POST /auth/case-links/request, /confirm | 이메일 접속 링크 재발급·확인 및 CASE 세션 발급 |
| GET /case-workspace/{shipmentId} | CASE 세션의 초대받은 건 조회 |
| POST /case-workspace/{shipmentId}/documents | CONTRIBUTOR의 운송 문서번호 등록 |

유효하지 않은 인증은 401, 인증은 됐지만 작업 권한이 없으면 403, 범위 밖 자원 조회는
존재를 노출하지 않도록 404, 상태 경쟁·제약 충돌은 409로 일관되게 처리한다.
공개 링크 발급 응답은 이메일·초대 존재 여부를 드러내지 않는다.

## 6. 관리자 초기화와 이메일 발송

- 최초 시스템관리자는 일반 가입·웹 API로 선택하지 못한다.
- 별도 운영자 CLI/프로필로 이메일과 비밀번호를 입력받아 기존 사용자와 충돌을 검사하고
  시스템 역할을 부여한다. 기본 관리자 비밀번호, 소스 내 자격증명, 실행 때마다 자동 승격은 금지한다.
- 비밀번호는 비노출 입력으로 받고 해시만 저장한다. CLI 인수·로그에 평문을 남기지 않는다.
- 초기화는 명시 실행에 한정하고 재실행 시 중복 생성을 방지한다. 완료 이력을 기록한다.
- SMTP 등 발송 구현은 인터페이스로 분리한다. 개발 테스트에는 실제 발송 대신 테스트 어댑터를 쓴다.
- DB outbox에 발송 대기를 함께 저장하고 커밋 후 재시도한다. 원문 인증 토큰이 포함된 발송 데이터는
  제한된 보관 기간·접근 통제 및 암호화로 보호하고 발송 완료 후 제거한다.
- 실제 관리자 이메일, 실제 메일 제공자·발신 도메인·자격증명은 해당 운영 적용 단계에서 받는다.
  설계·로컬 테스트 과정에서 실제 이메일을 보내거나 계정을 생성하지 않는다.

## 7. 단계별 리팩토링 및 승인 기준

각 단계는 변경 요약·테스트 결과·남은 제약을 보고한 뒤 다음 단계 승인을 기다린다.
아래 중간 단계는 개발 순서이며, 신규 가입 승인 흐름은 3단계까지 통합 검증한 뒤 운영 적용한다.

| 단계 | 구현 범위 | 완료 기준 |
|---|---|---|
| 1. 권한·세션 기반 | 시스템 역할, 조직 없는 인증 컨텍스트, 세션 검증, 감사 기반, 관리자 초기화 명령 | 기존 화주 로그인 유지; 조직 없는 시스템관리자 인증; 역할 회수 즉시 차단; 공개 가입 승격 불가 |
| 2. 가입 승인 백엔드 | 신청 모델·이메일 확인·승인/반려 트랜잭션·outbox; 자동 OWNER 생성 제거 | 미승인 접근 차단; 승인 1회만 성공; 실패 롤백; 반려·재신청 이력 보존 |
| 3. 승인 화면 및 통합 | 신청 상태·이메일 확인 화면, 시스템관리자 검토 페이지, 프런트 인증 분기 | 신청부터 승인 후 화물 접근까지 E2E; API 직접 호출 우회 차단 |
| 4. 조직 직원 권한 | OWNER의 ADMIN 지정·해제, ADMIN의 제한된 직원 관리 | 조직 간 변경 차단; 마지막 OWNER 제거·자기 승격 차단; 변경 이력·기존 세션 반영 |
| 5. 외부 업체·초대 | 업체 연락처, 건별 담당자 3명 제한, 이메일 링크 인증·참여·철회 | 동시 초대로 제한 초과 불가; 다른 건 접근 차단; 토큰 재사용·만료 차단; 철회 즉시 반영 |
| 6. 운영 적용 준비 | 실환경 설정, 관리자 초기화 절차, 메일 발송 검증, 기존 데이터 전환·복구 절차 | 신규 DB·기존 DB 전환 검증, 배포 체크 결과 검토; 실제 적용은 명시 승인 후 |

2단계는 signup 응답 계약을 바꾸므로 3단계 완료 전 중간 결과를 운영에 배포하지 않는다.
4단계 직원 등록은 이메일 확인을 마친 기존 계정의 이메일 추가 방식으로 구현했다.
신규 등록·재활성화는 활성 조직 소속 한 곳으로 제한하며 직원 전용 신규 가입·초대는 후속 확장이다.
5단계 외부 권한은 VIEWER의 건별 운송 정보·문서번호 조회와 CONTRIBUTOR의 문서번호 추가로
구현했다. 화물 전체 수정·대표 문서 지정·최종 통관 승인·재초대는 허용하지 않는다.

### 7.1 단계 1 승인 시 실제 변경 대상

- AuthService, TokenService, CurrentActor: 공통 사용자 인증 및 컨텍스트별 권한 검사 분리.
- SecurityConfig, RefreshSession 및 repository: 시스템 역할 검사, 세션 목적·현재 권한 확인,
  refresh 경쟁 제어. 기존 조직 세션의 동작은 호환 테스트로 보존한다.
- identity 또는 platform 패키지: 시스템 역할·감사 엔티티, 명시 실행 관리자 초기화 명령.
- 새로운 Flyway 파일: 시스템 역할·감사 테이블, 세션 확장·기존 세션 매핑.
- 보안·서비스·DB 통합 테스트 및 초기화 명령 사용 문서.
- 이 단계에서는 가입 승인 화면, 외부 초대 기능, 실제 관리자 계정 생성은 수행하지 않는다.

## 8. 마이그레이션·검증·복구

- 적용 이력을 가진 V01~V13은 수정하지 않고 새 Flyway 버전을 추가한다.
  실제 버전 번호는 구현 시 저장소의 최신 번호를 확인해 정한다.
- 확장 컬럼 추가 → 기존 데이터 백필 → 중복·참조 검증 → 제약 적용 순으로 진행한다.
- 기존 refresh 세션은 ORGANIZATION으로 매핑한다. session_id 없는 이전 access 토큰은 전환 시
  401로 처리한다. 유효한 기존 refresh 쿠키는 검증 후 신규 access 토큰으로 교환할 수 있고,
  그렇지 않으면 다시 로그인한다. 오래된 토큰을 무검증 허용하는 호환 경로는 만들지 않는다.
- 기존 활성 조직·OWNER·화물은 유지한다. 사용자 및 연락처를 임의로 병합·삭제하지 않는다.
- DB 복제본에서 기존 데이터 마이그레이션과 신규 DB 전체 마이그레이션을 모두 검사한다.
- PostgreSQL을 사용하는 통합 테스트로 잠금·부분 유일 제약·동시 승인·refresh 회전·3명 제한을 검증한다.
- 컨트롤러 권한 테스트는 SYSTEM_ADMIN/OWNER/ADMIN/OPERATOR/VIEWER/대기/외부 및 다른 조직 조합을 포함한다.
- 프런트 테스트는 설계 시점의 2개에서 6단계 준비까지 32개로 확장했다. 대기·반려·승인·역할별
  진입·직원 관리와 외부 초대·접속·철회 흐름을 검증한다.
- 배포 전 DB 백업과 복원 리허설, 이전 앱과 스키마 호환 범위를 기록한다.
  기능 활성화 뒤에는 단순 코드 롤백으로 자동 OWNER 가입이 다시 열리지 않도록 신규 가입·승인을
  일시 중단하고 전진 수정 또는 검증된 복원 절차를 사용한다.

## 9. 이후 결정할 운영 항목

- 실제 시스템관리자 이메일 및 관리자 계정 보강 인증 정책.
- 조직 실재·신청자 대표 권한을 확인할 자료와 승인 기준, 중복 사업자 신청 처리.
- 메일 발송 제공자, 발신 도메인, 링크·세션 기한의 운영값.
- 소유권 이관·복구 시 확인 자료와 승인 절차.
- 외부 업체별 담당자 역할, 공용 이메일 허용 범위, 중요 업무의 재인증 기준.
- 거래 단위 도메인 도입 시 선적 참여 권한과의 연결 정책.

위 항목은 단계 1의 코드 기반 작업을 막지 않는다. 실제 발송·계정 생성·운영 적용 또는
해당 기능 구현 전에 필요한 항목을 확정한다.
