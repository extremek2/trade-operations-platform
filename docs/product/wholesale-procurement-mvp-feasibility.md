# 도매 사이트 기반 발주 MVP 실현 가능성

- 검토일: 2026-09-22
- 범위: 직접 공급처 계약 전, 사업자 도매 사이트의 상품을 조회하고 구매 판단부터 국내 입고까지 잇는 첫 버전
- 상태: 샘플 조회·제안 검토·국내 발주 인계·선적 없는 입고의 첫 구현 완료. 실제 도매 계정/API 키로 호출하거나 결제한 결과는 아님.

## 결론

**가능하다. 첫 연동은 도매꾹 Open API의 상품 조회로 한정한다.** 조회된 가격은 발주 확정가가 아니라 확인 시점의 제안값으로 다룬다. 사용자가 사업자 계정으로 원 사이트에서 주문·결제하고, 우리 시스템에는 주문번호·실결제액·입고 수량을 기록한다. 자동 주문은 후순위다. 도매꾹은 상품 목록·상세 Open API를 제공하지만 주문서 생성은 별도 승인되는 Private API이며 별도 샌드박스가 없다. [Open API 이용 방법](https://docs.channel.io/domeggook_api/ko/articles/bd7265d8), [주문서 생성](https://docs.channel.io/domeggook_api/ko/articles/%EC%A3%BC%EB%AC%B8%EC%84%9C-%EC%83%9D%EC%84%B1-68288eeb)

## 인바운드와 아웃바운드 경계

이 문서에서는 **우리 플랫폼을 기준으로 정보가 들어오고 나가는 방향**으로 정의한다. 물류의 국내 입고·고객 출고는 별도 상태다.

| 경계 | 동작 | 승인/기록 |
|---|---|---|
| 인바운드 | 도매 사이트 API 상품·가격 조회, 사이트 URL 수동 등록, 공급처 이메일 회신·Excel/PDF 견적 수집 | 원본·조회 시각·출처 보존 → 정규화된 제안 → 사용자 확인 |
| 내부 판단 | 수량·옵션·MOQ·배송비를 반영한 예상 원가, 구매 품목 선택, 내부 PO 승인 | `APPROVED`는 내부 승인이고 외부 주문 성립이 아님 |
| 아웃바운드 | 공급처 문의 문안을 Gmail 작성 창으로 인계, 도매 사이트 구매 페이지로 인계, 이후 별도 승인이 있을 때 주문 API | Gmail 임시보관함 저장 여부는 현재 시스템에서 확인하지 못함. 이메일 발송·외부 주문·결제는 자동 실행하지 않음 |
| 물류 | 국내 매입은 국내 입고, 해외 매입은 선적·통관 후 입고, 위탁은 판매자 출고 | 발주와 분리된 경로별 증빙·수량 상태 |

`자료 유입 채널`과 `조달/이행 경로`를 하나의 enum에 섞지 않는다.

| 자료 유입 채널 | 초기 처리 | 가능한 조달 경로 |
|---|---|---|
| 사업자 사이트 + 공식 조회 API | 구조화된 가격·옵션·MOQ 스냅샷 | 국내 재고 매입 우선; 수입은 후속 |
| 사업자 사이트 + API 없음 | 상품 URL과 사용자가 확인한 가격·조건 | 국내 재고 매입 |
| 공급처 이메일 | 본문·첨부를 수동 접수, 문의는 Gmail 작성 창으로 인계 | 국내 매입 또는 수입 |
| Excel/CSV/PDF 견적 | 기존 파일 접수·검토 | 국내 매입 또는 수입 |

사이트 운영자와 실제 상품 판매자가 다를 수 있으므로 `platform`, `sellerId`, `supplier`를 구분한다. 현재 PO는 한 공급처의 선택 견적에서 생성되므로 판매자가 다른 상품은 첫 버전에서 PO를 나눈다.

```text
도매 사이트 API/URL ─┐
이메일·Excel·PDF ───┘
          ↓
원본 스냅샷 → 제안 행 확인 → 구매 품목 선택 → 예상 원가 → 내부 PO 승인
          ↓                                              ↓
     출처·시각 보존                       외부 사이트 주문·결제(사용자 직접)
                                                         ↓
                                    주문번호/실결제액 기록 → 국내 입고
```

## 공식 API 후보

| 우선순위 | 후보 | 공식 문서로 확인된 범위 | 판단 |
|---|---|---|---|
| 1 | **도매꾹** | Open API 키로 `getItemList`(`market=dome`)와 상품 상세 조회. 목록에 가격·MOQ·사업자 전용 여부·배송비·상품 URL, 상세에 수량별 단가·재고가 있다. `comOnly=true`는 사업자 회원만 구매 가능하다. [상품 목록](https://docs.channel.io/domeggook_api/ko/articles/43780628), [상품 상세](https://docs.channel.io/domeggook_api/ko/articles/933abc24) | 국내 도매 매입의 읽기 전용 실증 1순위. 사업자 전용 상품의 실제 구매에는 사업자 회원 자격이 필요하다. |
| 2 | **orosy** | 일본 도매 상품 검색·상세·국가별 배송 가능 여부 API. 가입 후 사업 검토가 있고 실제 상품·가격과 API 키는 승인 후 제공된다. 승인 전에는 데모 데이터의 테스트 모드가 있다. [가입·API 안내](https://wholesale-portal.orosy.com/en/guide/) | 해외 소싱 2순위. 사업 심사, 배송 가능 국가, 엔화 결제, 수입 비용이 첫 국내 MVP보다 복잡하다. |

도매꾹 `market=supply`(도매매)는 같은 API에서 구분되지만 첫 구현은 `market=dome`만 사용한다. 다른 도매 사이트는 **구매자용 상품 조회 API의 공식 문서와 계정 자격을 확보한 뒤** 후보에 추가한다. API가 없는 사이트는 로그인 자동화나 화면 수집을 전제로 하지 않고 URL·수동 입력 경로를 사용한다.

## 첫 구현 범위

1. 서버에서 사용자 키워드로 도매꾹 목록을 조회하고 선택한 상품만 상세 조회한다. API 키는 서버에만 저장하며 `aid`가 포함된 요청 URL을 로그에 남기지 않는다. 도매꾹은 분당 180회/하루 15,000회 제한과 HTTP 200 응답 본문의 오류 코드가 있으므로 호출량 제한·오류 파싱을 포함한다. [표준 오류 메시지](https://docs.channel.io/domeggook_api/ko/articles/7a511249)
2. 제안 스냅샷에 플랫폼·판매자 ID·외부 상품번호/URL·조회 시각·원본 응답 해시, 옵션, MOQ, 수량 구간 단가, 통화, 과세 구분, 배송 조건, 조회 당시 재고를 보존한다. 수량 구간 단가는 단일 가격으로 평탄화하지 않는다. 가격/재고·배송 조건은 사이트 주문 직전에 다시 확인한다. [상품 상세](https://docs.channel.io/domeggook_api/ko/articles/933abc24)
3. 기존 `SupplierOfferDraft → SupplierQuote → CostScenario → PurchaseOrder`를 재사용한다. API 응답도 오류·누락·가격 변경·옵션 불일치가 있으면 사용자 확인 대상으로 보낸다.
4. 내부 PO 승인 후 원 사이트 상품 링크를 제공한다. 사용자가 직접 주문·결제한 뒤 외부 주문번호, 확정 수량, 실결제액, 주문 증빙을 기록한다. `내부 승인`과 `외부 주문 완료`를 별도 상태로 둔다.
5. 국내 매입은 선적 객체 없이 입고를 기록하는 경로를 만든다. 이 경로가 없으면 현재 시스템에서 국내 도매 상품을 재고로 받을 수 없다.

첫 검증용 상품군은 배송과 옵션이 단순한 비규제 생활용품·문구 등으로 제한하는 것이 합리적이다. 이는 API의 상품 적합성 보장이 아니라 테스트 비용을 낮추기 위한 제안이다. 구매 가능 여부, 판매 제한, 세금·반품 조건은 각 상품에서 확인해야 한다.

### 현재 코드와의 차이

| 이번 구현 | 남은 검증·고도화 |
|---|---|
| `SourceArtifact.SourceType.API`, `ExtractionRun.Method.API`와 XML 원본·해시·조회 시각 보존 | 실제 API 응답으로 필드 대응 확인, 옵션과 구간가의 구조화 |
| 내부 PO에 국내 매입/수입 경로와 외부 주문 상태·번호·확정 금액 분리 | 실제 주문 증빙, 상품 페이지 연결, 주문 직전 가격·재고 재조회 |
| 국내 PO 행에서 선적 없이 부분·전량 입고 | 배송/반품 예외와 동시 입고 검증 고도화 |
| 기존 원가 모델 재사용 | 국내 배송비·수량 구간 단가·부가세를 독립적으로 계산하는 입력 간소화 |
| CSV/XLSX/PDF 수동 제안과 Gmail 작성 창 링크 유지 | Gmail 임시보관함 실제 저장 확인; 이메일 발송·자동 수신은 이번 범위 밖 |

샘플 데이터는 판매자 이름에 `샘플`을 표시하고 원 사이트 링크를 제공하지 않는다. 샘플 제안으로 만든 PO는 실제 외부 주문으로 전환할 수 없으며, 따라서 실제 입고 재고도 만들 수 없다.

## 재개할 때 우선순위

1. **P0 — 실제 도매꾹 읽기 전용 실증:** 사용자 계정/API 키를 서버 환경변수 `DOMEGGOOK_API_KEY`로 설정한 뒤 상품 검색·상세 20~30건을 사이트 화면과 대조한다. API 키를 브라우저에 넣지 않는다. 실제 주문 API는 호출하지 않는다.
2. **P1 — 가격·옵션·원가 정확도:** 수량별 단가와 옵션·배송비를 정규화하고 희망 수량에 맞는 가격을 계산한다. 구매 직전 재조회 결과가 스냅샷과 다르면 다시 승인받는다. 국내 매입 원가 입력에서 불필요한 수입 항목을 걷어낸다.
3. **P1 — 실제 주문·입고 증빙:** 도매 사이트 주문번호와 결제내역을 PO에 연결하고, 부분 입고·품절·취소 상황을 실제 사례로 검증한다. 현재는 주문번호와 금액을 수동 기록한다.
4. **P2 — 다른 조달 경로:** API 없는 사업자 사이트의 URL/수동 입력과 이메일·Excel 견적을 같은 제안 원장으로 유지하면서, 구매자용 공식 API가 확인된 사이트만 어댑터로 추가한다. 일본 도매 API는 국가별 배송·사업 심사·수입 비용이 확인된 뒤 검토한다.

현재 자동 검증은 도매꾹 형식의 **고정 샘플 응답**과 국내 매입 통합 흐름이다. 실제 API 응답의 호환성, 실제 사업자 도매가, 실제 구매 가능성은 미검증이다.

## 검증 순서와 통과 기준

1. **계정 없이**: 공식 응답 형식의 고정 샘플로 목록·상세 매핑, 고정가/구간가, MOQ, 사업자 전용, 품절, 오류 응답을 검증한다. 이 단계는 실시간 도매가 검증이 아니다.
2. **도매꾹 계정·API 키 확보 후**: `getItemList`와 상세 조회만 호출한다. `comOnly=true` 상품과 일반 상품을 구분하고, 20~30개 후보의 가격·MOQ·옵션·배송비를 사이트 표시와 대조한다. 20~30개는 제안한 실증 규모다.
3. **사업자 구매 자격 확인 후**: 실제 구매 가능한 상품 한 건을 사용자가 사이트에서 직접 구매하고 외부 주문번호·실결제액·입고 수량을 기록한다. 그 전에는 구매 완료를 주장하지 않는다.
4. 통과 조건(제안): 선택 품목의 출처·조회 시각 100% 기록, MOQ/구간가 계산 불일치 0건, 내부 승인만으로 외부 주문/결제 0건, 수량을 초과하는 입고 0건. 표본에서 실패한 필드는 사용자 확인 대상으로 전환한다.

도매꾹은 별도 샌드박스가 없으므로 첫 실증에서 주문 API를 호출하지 않는다. `orosy`는 사업 승인 전 테스트 모드로 화면 흐름을 살필 수 있지만 실제 도매가 검증은 승인 후 별도 단계다. [도매꾹 Open API 이용 방법](https://docs.channel.io/domeggook_api/ko/articles/bd7265d8), [orosy 가이드](https://wholesale-portal.orosy.com/en/guide/)

## 결정이 필요한 실제 전제

- 사업자 등록 및 도매 사이트의 사업자 회원 자격이 있는지. 없으면 공개 API 연동/샘플 검증까지만 진행하고 사업자 전용 상품의 실제 구매는 대기한다.
- 도매꾹 API 키를 발급받을 수 있는지. 키가 없으면 라이브 API 결과를 주장할 수 없다.
- 첫 판매 채널과 상품군. 이는 구매 가능성·판매 제한·원가 검증용 상품 표본 선택에 필요하다.
- 해외 소싱 확장 시 사업 웹사이트와 `orosy` 계정 심사·배송 가능 국가·수입 비용을 별도 확인한다.
