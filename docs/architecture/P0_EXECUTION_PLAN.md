# 코어 도메인 실행 계획

- 상태: P0~P5 첫 수직 사이클 완료, 상세 운영 규칙 확장 대기
- 기준 결정: [ADR-0002](ADR-0002-core-domain-and-clean-baseline.md)
- 최종 검토일: 2026-09-15

이 계획의 원칙은 필요한 사용자 흐름과 Aggregate를 같은 수직 슬라이스에서 추가하는 것이다.
소형 ERP에 필요할 것 같다는 이유만으로 빈 테이블, 범용 상위 엔터티, 자동화 인프라를 미리 만들지
않는다.

## 현재 기준선

```text
React -> Spring Boot -> PostgreSQL
```

- 업무 소유 경계: `Organization`
- 상품 원장: 후보와 판매 상품을 합친 `Product`
- 거래처 원장: 공급사와 협업 업체를 합친 `BusinessPartner` + 역할
- 소싱: `SupplierQuote` + `SupplierQuoteLine`
- DB 설치 이력: V1 기준선부터 V6 실제 원가·판매·판단까지 순방향 migration
- 자동화 Worker, Redis, Python DB Writer: 현재 런타임에 없음

### 다품목 발주 입력 설계

다품목 발주는 `직접 입력`, `Excel/CSV 업로드`, `상품 URL 입력`을 같은 임시 품목 행으로
정규화한 뒤 사용자가 미리보기에서 확인하고 확정한다. 외부 입력이 `Product`, 견적 또는 원가
스냅샷을 바로 생성하거나 기존 원장을 덮어쓰지 않는다.

```text
직접 입력 ─┐
Excel/CSV ─┼→ ImportBatch / ImportRow → 행 검증·상품 매칭 → 사용자 확정 → PO Line
상품 URL ──┘
```

각 임시 행은 최소한 입력 출처, 원본 행/URL 참조, 상품명, 공급처 SKU, 수량·단위, 단가·통화,
원산지, 기존 상품·견적·원가안 매칭 상태와 행별 오류를 보존한다. 기존 상품과 자동 매칭되지 않은
행, 단위·통화가 불명확한 행, 완성된 예상 원가가 없는 행은 `REVIEW_REQUIRED`로 남기고 발주
승인을 제한한다.

Excel/CSV는 다음 순서로 도입한다.

- 조직별 업로드 배치, 파일 해시와 행 번호로 재업로드·중복을 식별한다.
- 서버는 수식이나 매크로를 실행하지 않고 허용된 셀 값만 읽는다.
- 필수 열, 숫자 형식, 통화·단위, 중복 SKU 오류를 행별로 보여준다.
- 미리보기 승인 전에는 업무 원장에 반영하지 않고, 일부 정상 행만 확정할지도 사용자가 선택한다.
- 초기 템플릿과 실제 공급사 양식의 열 매핑을 분리해 템플릿 변경이 도메인 모델을 바꾸지 않게 한다.

상품 URL은 먼저 `URL + 확인일 + 사용자가 확인한 상품값`을 저장하는 폴백부터 제공한다. 자동
추출은 공개 접근과 이용조건을 확인한 허용 사이트용 어댑터로만 확장하며 로그인 우회나 임의 사이트
대량수집은 하지 않는다. 서버가 URL을 조회할 때는 사설 IP·로컬 주소·과도한 리다이렉트·대용량
응답을 차단하고, 원본 URL·수집시각·추출값·사용자 수정값을 분리해 보존한다. 추출 실패 시에도
URL을 근거로 남기고 수동 입력으로 계속 진행할 수 있어야 한다.

구현 순서는 다음과 같다.

1. 다품목 PO와 행별 견적·원가 스냅샷, 직접 입력 미리보기
2. Excel/CSV 업로드 미리보기·행 오류·확정·멱등 재업로드
3. 상품 URL 근거 저장과 사용자 확인 입력
4. 실제 반복 사이트가 확인된 뒤 허용 도메인별 자동 추출 어댑터

## 조건부 인프라

다음은 요구가 발생하기 전에는 추가하지 않는다.

- ProductVariant: 실제 옵션별 SKU·재고가 필요할 때
- TradeCase: 여러 Aggregate의 장기 진행을 조정할 필요가 있을 때
- Outbox/Worker/Redis: 반복 수동 작업이 측정되고 비동기 자동화가 선택될 때
- Object Storage: 실제 문서 업로드 흐름을 구현할 때
- 별도 DB 스키마와 서비스: 독립 배포·권한·부하 요구가 확인될 때

## 공통 완료 게이트

각 슬라이스는 다음을 만족해야 완료다.

- 인증 컨텍스트에서 조직 범위를 결정하고 요청 Body의 조직 ID를 신뢰하지 않는다.
- 다른 조직 엔터티 참조가 API와 통합 테스트에서 차단된다.
- 상태 전이, optimistic lock, 중복 키와 nullable 의미가 테스트된다.
- 새 테이블은 실제 API 또는 운영 작업의 소유자가 있다.
- 빈 PostgreSQL에서 Flyway와 JPA validation이 통과한다.
- 백엔드·프론트 전체 회귀와 Compose 문법 검사가 통과한다.

## 파괴적 작업과 승인 경계

- 이번 개발 DB 볼륨 삭제는 ADR-0002 범위에서 승인됐다.
- 운영/외부 DB, 다른 Docker 볼륨, 실제 메일 발송, 외부 서비스 공개는 별도 승인 없이는 수행하지 않는다.
- 데이터가 생긴 뒤 migration 재작성, 대량 삭제, 테넌트 병합은 반드시 별도 전환 계획과 백업을 요구한다.
