# 코어 도메인 실행 계획

- 상태: P0~P5 첫 수직 사이클 완료, P6 제안 접수부터 다품목 거래 사이클과 CSV/XLSX 결정론적 파서 구현
- 기준 결정: [ADR-0002](ADR-0002-core-domain-and-clean-baseline.md)
- 최종 검토일: 2026-09-19

이 계획의 원칙은 필요한 사용자 흐름과 Aggregate를 같은 수직 슬라이스에서 추가하는 것이다.
소형 ERP에 필요할 것 같다는 이유만으로 빈 테이블, 범용 상위 엔터티, 자동화 인프라를 미리 만들지
않는다.

## 현재 기준선

```text
React -> Spring Boot -> PostgreSQL
```

- 업무 소유 경계: `Organization`
- 상품 원장: 후보와 판매 상품을 합친 `Product`
- 거래처 원장: 공급사와 협업 업체를 합친 `BusinessPartner` + 역할
- 소싱: `SupplierQuote` + `SupplierQuoteLine`
- DB 설치 이력: V1 기준선부터 V10 CSV/XLSX 제안 파일 수집까지 순방향 migration
- 자동화 Worker, Redis, Python DB Writer: 현재 런타임에 없음

## P6 — 공급 제안 수집·승인·구매 선택

상태: 수동 원본 접수·추출 확인·행별 구매 선택·상품/견적·예상 원가·다품목 발주 연결 구현, 실제 파일 파서 전

이 단계의 목적은 발주 행을 대량 입력하는 데 있지 않다. 공급처가 여러 형식으로 전달한 도매 상품
제안을 조직 내부에서 검토 가능한 상품 제안으로 디지털화하고, 사용자가 살 품목을 선택한 뒤 기존
예상 원가·발주·입고·판매 흐름으로 넘기는 데 있다.

```text
API ────────────────┐
Excel / CSV ────────┤
PDF / 스캔 이미지 ─┼→ SourceArtifact → ExtractionRun → SupplierOfferDraft
이메일 본문·첨부 ──┤                                  ↓ 추출 확인
상품 URL / 수동 ────┘                           SupplierOffer / OfferLine
                                                         ↓ 구매 품목 선택
                                                  PurchaseSelection
                                                         ↓ 원가·발주 승인
                                                  기존 P2~P5 사이클
```

Orosy처럼 API가 있는 공급처는 OCR을 거치지 않고 구조화 데이터를 표준 필드로 매핑하여 자동
검증까지 거의 직행한다. API가 없는 공급처는 Excel, PDF, 이메일 또는 URL에서 같은 초안을 만든다.
입력 방식이 달라도 추출 확인 이후의 품목 선택·원가 계산·발주·입고·판매 흐름은 하나로 유지한다.

### 승인 경계

서로 다른 책임을 한 번의 승인으로 합치지 않는다.

1. **추출 확인:** 원본에서 읽은 상품, 옵션, 단위와 가격이 맞는지 확인한다.
2. **구매 품목 선택:** 승인된 공급 제안 중 실제 검토하거나 살 품목과 희망 수량을 고른다.
3. **발주 승인:** 최신 가격·재고·MOQ와 예상 원가를 확인하고 실제 지출을 승인한다.

신뢰할 수 있는 API 응답은 정책과 검증 결과에 따라 추출 확인을 자동 통과할 수 있다. 가격 변경,
품절, MOQ 위반, 옵션 불일치와 필수 값 누락은 `REVIEW_REQUIRED`로 보낸다. 구매 품목 선택과 발주
승인은 별도 자동화 정책을 도입하기 전까지 사용자가 수행한다.

### 입력과 원본 보존

- `SourceArtifact`는 조직, 공급처, 입력 유형, 원본 파일 또는 URL, 콘텐츠 형식, 파일 해시,
  수신 시각을 보존한다.
- `ExtractionRun`은 파서/OCR/AI 방식과 버전, 실행 상태, 오류를 기록하며 재실행 결과로 기존
  승인 데이터를 덮어쓰지 않는다.
- 초안 행은 상품명, 공급처 SKU, 옵션, 수량·단위, MOQ, 수량 구간, 단가·통화, 세금·배송 조건,
  원산지, 재고, 견적 유효일과 기존 상품 매칭 상태를 nullable 값으로 가진다.
- 추출 필드는 페이지·표·셀·이메일 구간 같은 원본 위치, 신뢰도와 사용자 수정 이력을 연결한다.
  알 수 없는 값은 0이나 임의 기본값으로 확정하지 않는다.
- 사용자가 승인하기 전에는 `Product`, `SupplierQuote`, 원가 스냅샷 또는 PO를 생성하거나 기존
  원장을 덮어쓰지 않는다. 정상 행만 골라 승인할 수 있고 제외된 행도 원본과 함께 남긴다.

### 파싱·OCR·AI 원칙

비용과 오인식을 줄이기 위해 결정론적 파서를 먼저 사용하고 필요한 구간에만 OCR과 AI를 적용한다.

1. API와 허용된 구조화 URL 데이터는 공급처별 어댑터로 표준화한다.
2. Excel/CSV는 수식이나 매크로를 실행하지 않고 허용된 셀 값만 읽는다.
3. 텍스트 PDF와 이메일 본문은 포함된 텍스트와 표를 먼저 추출한다.
4. 스캔 PDF와 이미지만 OCR을 실행한다.
5. AI는 열 매핑, 깨진 표 복원, 단위·옵션 해석과 누락 후보 제시에 제한한다.
6. 통화·단위·합계·MOQ·중복·기존 상품 매칭은 결정론적 규칙으로 다시 검증한다.

상품 URL은 먼저 `URL + 확인일 + 사용자가 확인한 상품값`을 저장하는 폴백을 제공한다. 자동
추출은 공개 접근과 이용조건을 확인한 허용 사이트용 어댑터로만 확장하며 로그인 우회나 임의 사이트
대량수집은 하지 않는다. 서버 조회 시 사설 IP·로컬 주소·과도한 리다이렉트·대용량 응답을 차단한다.

### 구현 순서와 내일 재개 지점

세부 파서보다 먼저 하나의 공급 제안이 기존 거래 사이클 끝까지 연결되는 뼈대를 검증한다.

1. `SourceArtifact`, `ExtractionRun`, `SupplierOfferDraft`와 초안 행의 최소 Aggregate·migration
2. 직접 입력 또는 고정 샘플 어댑터 → 추출 확인 → `Product`·`SupplierQuote` 전환
3. 승인된 제안 행 일부 선택 → 기존 원가 시나리오·다품목 PO → P3~P5 흐름 연결
4. 원본/추출값 나란히 보기, 행 수정·제외·부분 승인 UI와 조직 격리·상태 전이 테스트
5. Excel/CSV와 텍스트 PDF 결정론적 파서, 멱등 재업로드와 행별 오류
6. 스캔 PDF·이미지 OCR, 이메일 본문·첨부 수집
7. 실제 API 자격과 문서가 확보된 공급처부터 어댑터 추가 및 자동 추출 확인 정책 적용

첫 완료 기준은 고정 샘플 공급 제안 한 건을 등록하고 일부 품목만 승인·
선택하여 기존 예상 원가부터 재발주 판단까지 같은 조직 범위에서 연결하는 통합 테스트다. 실제 OCR,
외부 이메일 수신과 Orosy 운영 API 호출은 공통 흐름이 확인된 뒤 각각의 어댑터로 추가한다.

- 조직 범위, 중복 원본, 낙관적 잠금, 확인 전 상품·견적 원장 미생성을 통합 테스트로 검증했다.
- 아직 구매 품목 선택, `Product`·`SupplierQuote` 전환, 다품목 발주, 실제 파일·파서·OCR·외부 API는 구현하지 않았다.
- 다음 시작점은 확인된 행 중 일부를 구매 후보로 선택해 기존 견적·예상 원가로 넘기는 계약이다.
- 검증: 백엔드 전체 115개, 프런트엔드 전체 46개 테스트와 개발 Compose 문법 검사 통과.

### P6 구매 품목 선택 결과

- V8에 `PurchaseSelection`과 선택 행을 추가해 원본 제안 행, 희망 수량, 상품·견적 행의 연결을 보존했다.
- 확인된 행 중 일부만 선택하고 나머지는 이후 별도 선택할 수 있다. 제외된 행, MOQ 미달, 중복 선택과
  다른 조직 상품 참조는 거절한다.
- 선택 시 신규 상품 또는 같은 조직의 소싱 중 상품을 사용하고, 선택한 행만 작성 중 견적으로 만든다.
  견적 수신은 사용자가 별도로 처리한다.
- 공급 제안 화면에서 등록·행별 검토·추출 확인·구매 선택을 수행하고, 예상 원가 화면에는 선택 희망
  수량을 가져온다.
- 다음 시작점: 선택한 여러 행을 하나의 다품목 PO로 발주 승인하고 부분 선적·입고·실제 원가까지
  연결한다. 실제 파일 파서·OCR·이메일·외부 API는 그 뒤에 추가한다.
- 검증: 백엔드 전체 116개, 프런트엔드 전체 49개 테스트, 프런트엔드 배포 빌드와 개발 Compose
  문법 검사 통과.

### P6 다품목 발주 연결 결과

- V9에서 발주 머리의 단일 원가 시나리오 연결을 발주 행별 연결로 이관했다.
- 같은 공급 견적의 최신 완성 원가안 여러 개만 하나의 발주로 묶고, 중복·재사용·다른 견적 혼합을 차단한다.
- 화면에서 여러 원가안을 선택하고 발주 품목별로 선적을 배정하며, 입고·로트·실제 원가 흐름을 유지한다.
- 재발주 판단은 발주의 첫 상품을 암묵적으로 쓰지 않고 판단 대상 상품을 명시한다.
- 다음 시작점: 파일 해시와 원본 보존을 포함한 Excel/CSV 결정론적 파서와 멱등 재업로드.
- 상세 기록: [P6 세 번째 단계](../engineering/supplier-offer-stage-3.md)

### P6 CSV/XLSX 파일 수집 결과

- V10에서 2MB 이하 CSV/XLSX 원본 바이너리·파일명·크기·콘텐츠 형식·SHA-256을 보존한다.
- UTF-8 CSV와 XLSX 첫 표시 시트를 수식·매크로 실행 없이 읽고, 지원 헤더를 결정론적으로 매핑한다.
- 형식 전체의 문제는 업로드를 거절하고 값 문제는 행별 오류로 남겨 사용자가 수정·확인 또는 제외한다.
- 같은 조직·공급처·파일 해시를 다시 올리면 새 원본과 초안을 만들지 않고 기존 초안을 반환한다.
- 합성 fixture로 구현 계약을 검증했으며 실제 공급처 파일 변형은 아직 확인하지 않았다.
- 다음 시작점: 익명화한 실제 공급처 CSV/XLSX로 헤더·날짜·병합 셀 변형을 수집하거나 텍스트 PDF 파서를 추가한다.
- 상세 기록: [P6 네 번째 단계](../engineering/supplier-offer-stage-4.md)

## 조건부 인프라

다음은 요구가 발생하기 전에는 추가하지 않는다.

- ProductVariant: 실제 옵션별 SKU·재고가 필요할 때
- TradeCase: 여러 Aggregate의 장기 진행을 조정할 필요가 있을 때
- Outbox/Worker/Redis: 반복 수동 작업이 측정되고 비동기 자동화가 선택될 때
- Object Storage: 현재 2MB 이하 제안 파일은 PostgreSQL에 보존한다. 파일 크기·보관량이 커질 때 선택·추가한다
- 별도 DB 스키마와 서비스: 독립 배포·권한·부하 요구가 확인될 때

## 공통 완료 게이트

각 슬라이스는 다음을 만족해야 완료다.

- 인증 컨텍스트에서 조직 범위를 결정하고 요청 Body의 조직 ID를 신뢰하지 않는다.
- 다른 조직 엔터티 참조가 API와 통합 테스트에서 차단된다.
- 상태 전이, optimistic lock, 중복 키와 nullable 의미가 테스트된다.
- 새 테이블은 실제 API 또는 운영 작업의 소유자가 있다.
- 빈 PostgreSQL에서 Flyway와 JPA validation이 통과한다.
- 백엔드·프론트 전체 회귀와 Compose 문법 검사가 통과한다.

## 파괴적 작업과 승인 경계

- 이번 개발 DB 볼륨 삭제는 ADR-0002 범위에서 승인됐다.
- 운영/외부 DB, 다른 Docker 볼륨, 실제 메일 발송, 외부 서비스 공개는 별도 승인 없이는 수행하지 않는다.
- 데이터가 생긴 뒤 migration 재작성, 대량 삭제, 테넌트 병합은 반드시 별도 전환 계획과 백업을 요구한다.
