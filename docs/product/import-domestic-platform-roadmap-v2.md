# 수입·국내 소싱·국내 판매 플랫폼 고도화 로드맵 v2

- 작성일: 2026-09-08
- 최종 검토일: 2026-09-12
- 상태: 현재 코드와 문서를 확인한 구현 계획. 회원·권한 1~5단계와 6단계 격리 리허설은 완료됐고 실제 운영 적용은 대기 중이다. 이후 업무 모듈은 구현 전이다.
- 범위: 국내외 상품 발굴 → 국내 도매/위탁 또는 해외 매입 → 수입 운영·전문가 협업 → 국내 판매·재매입
- 제외: 수출, 해외 판매, 전면 ERP/WMS, 실제 발주·송금·판매를 대신 수행하는 자동 실행
- 기존 자산: 회원·조직·가입 승인·건별 외부 참여와 선적 관리
- 기준 관계: 이 문서가 기존 `domestic-product-validation-module-v1.md`의 범위·개발 순서·수입 진입 조건을 대체한다. 해당 문서의 입력 필드와 계산·검증 세부 내용은 충돌하지 않는 부분에서 참조한다.
- 기존 `trade-operations-domain-v1.md`는 수입 운영의 상세 도메인 기준으로 유지한다. 전체 도메인 설계와 구현된 기능을 구분한다.

## 1. 하나의 플랫폼, 두 가지 매입 경로

```text
                         국내외 트렌드·직접 발굴
                                  ↓
                       상품군·구매 가설·국내 수요 근거
                                  ↓
                      국내외 공급처·문의·견적·샘플
                                  ↓
                        원가·판매 요건·매입 판단
                       ↙                    ↘
             국내 도매/위탁 매입             해외 매입·수입 거래
                       ↓                    ↓
               국내 입고/위탁 출고      PI·CI·송금·선적 품목 연결
                       ↓                    ↓
                       │           기존 포워더·관세사 협업
                       │                    ↓
                       │              통관·국내 입고
                       ↘                    ↙
                        실제 비용·국내 판매 결과
                                  ↓
                           재매입·재소싱·중단
```

혼자 사업을 운영하되 포워더·관세사와 필요한 정보를 공유하는 플랫폼이다. 모든 전문 업무를 사용자가 직접 처리하거나 소프트웨어가 대신 수행한다는 의미는 아니다.

해외 상품부터 시작할 수 있으며 국내 위탁 판매 이력을 수입의 필수 조건으로 요구하지 않는다. 국내 수요 확인은 매입 전 근거 조사이고, 실제 국내 판매 실적은 매입 후 검증할 수 있다. 첫 운영은 한 상품군·한 국내 판매 채널을 권장하지만 이를 영구 카테고리 제한으로 구현하지 않는다.

## 2. 현재 진행 상태: 자산과 공백

초기 확인 대상은 2026-09-08 작업 트리였고, 다른 PC의 변경과 네이버 쇼핑 검색 제거 커밋을 합친 뒤 2026-09-12 현재 코드를 다시 확인했다. 이때 백엔드 전체 92개와 Shopping Insight 단위 테스트 3개가 통과했다. 프런트엔드 전체·브라우저 E2E·운영 이미지 리허설은 다시 실행하지 않았으므로 아래 단계 문서의 과거 검증 수치와 구분한다. 다음 작업 시작 시에도 최신 상태를 다시 읽는다.

## 4. 개발 순서

### 0단계: 회원·권한 기준선 확정 — M1

- identity 1~5 구현과 6단계 격리 리허설 결과를 기준선으로 사용하며 반복 구현하지 않는다.
- 운영 준비는 기존 ops·테스트를 이어서 정리한다. 실제 배포를 새 기능 로컬 개발의 필수 조건으로 만들지 않는다.
- 새 업무 자료의 조직 격리, VIEWER 조회, OPERATOR 작성, CASE 건별 접근 경계를 확정한다.
- 현재 결과: 코드·테스트·운영 템플릿 기준선은 마련됐고 실제 환경 설정·계정·SMTP·배포는 대기 중이다.
- 완료: 권한 기준과 운영 적용 잔여 항목이 기록되고 신규 업무 경로에 재사용할 수 있다.

### 1단계: 연결 기준 확정 — M0 + M5의 설계 부분

- `후보 → 공급 견적 품목 → 매입 품목 → 수입 거래 품목 → 선적 배정 → 입고 → 판매` 식별 관계 확정.
- 국내 매입은 선적 없이 진행하고 위탁은 가짜 입고 재고를 만들지 않는다.
- 거래와 선적을 별도 객체로 두고, 기존 선적은 소싱 후보가 없어도 유지한다.
- 예측 비용, 실제 문서, 실제 비용의 버전과 소유 모듈을 결정한다.
- 기존 EXPORT enum/기록은 보존한다. 신규 업무 입력·서버 검증에서 수출 생성 제외를 계획하고 기존 데이터 열람은 별도로 처리한다.
- 산출물: 간단한 ERD, 필수 필드·ID/API 계약, 권한표, migration 계획. 전체 스키마를 한 번에 만들지 않는다.
- 완료: 국내·수입 예시 각 1건이 어떤 객체를 통과하는지 설명되고 같은 필드를 중복 소유하지 않는다.

### 2단계: 수동 발굴·국내 판매 근거 — M2

- 후보·상품군·국내외 관측 자료·국내 판매 근거를 수동 등록.
- 고정 트렌드 표시와 종료된 경로를 실데이터와 구분.
- 완료: API 없이 후보 1개가 공급처 조사로 넘어간다.

### 3단계: 공급처·문의·견적 — M3

- 국내 제조사·도매상·해외 업체와 연락 경로를 관리.
- 문의 준비/회신, MOQ·단가·통화·납기·판매 조건, 견적 버전과 샘플 기록.
- 도매 플랫폼 검색과 직접 문의를 동일 공급 후보 화면에서 연결.
- 완료: 국내외 견적을 동일 규격·수량 기준으로 비교하며 확인하지 않은 조건을 표시한다.

### 4단계: 원가·매입 검토 — M4

- 국내 매입 비용과 수입 후 총원가, 초기 현금 소요와 예상 공헌이익 계산.
- 거래 조건의 포함 비용·환율·공통비 배분·세금 처리 가정·품목별 수입/판매 확인 상태 기록.
- 완료: 한 후보의 국내/수입 시나리오에서 차이와 미확인 항목을 설명할 수 있다.

### 5단계: 매입·기존 수입 거래 연결 — M5

- 5A: 선택 견적에서 매입 품목 생성, 국내 매입 경로, 수입 거래 및 기존 선적 연결. 첫 종단 흐름에 필요한 최소 기능.
- 5B: PI/CI 품목 버전, 계획·실제 비교, 송금 계획/실제 기록, 수량·금액 배정 검사.
- 5C: 실제 필요가 생길 때 복수 PI/CI·분할/합배송 고도화. 모델의 확장성을 이유로 복잡한 UI부터 만들지 않는다.
- 완료: 소싱 자료를 재입력하지 않고 수입 운영으로 넘기며 계획/실제 변경과 중복 생성을 처리한다.

### 6단계: 기존 협업을 실제 업무로 확장 — M6

- 6A: 문서 첨부·버전·권한·검토 요청·정정·완료 근거. 기존 초대·CASE 세션 재사용.
- 6B: 담당자 task/issue, 마감일, 선적·통관 이벤트 수동 기록과 확인자.
- 6C: 실제 사례에 근거한 PI/CI 불일치·FTA·부분 도착 위험 검토 지원.
- 완료: 화주→포워더/관세사 요청→정정→확인 흐름이 한 건에서 수행되며 다른 거래 자료가 노출되지 않는다.

### 7단계: 입고·실제 원가 — M7

- 부분 입고·불량·부족·가용 수량, 실제 비용 배분과 잠정/확정 원가.
- 국내 매입과 수입을 연결하고 위탁은 공급자 출고 이력으로 처리.
- 완료: 매입 판단 당시 예상과 실제 도착 원가를 품목별로 비교한다.

### 8단계: 국내 판매·재매입 — M8

- 한 채널의 판매 실적 수동/CSV 입력, 주문·환불·배송·수수료·광고·응대 기록.
- 실제 공헌이익, 데이터 부족/중단/유지/확대/재소싱 판단.
- 완료: 공급 후보부터 판매 결과까지 출처가 이어지고 다음 매입 이유를 남긴다.

### 별도 진행: 수집 자동화 — M9

- M2/M3의 계약이 정해진 후 시작 가능. 처음에는 필요한 소스 하나만 연결.
- 조회 성공·자료 없음·실패·쿼터·비활성을 구분. 멱등 갱신과 보관 조건 적용.
- 완료: 수동과 같은 업무 객체로 자료가 들어오며 API 장애가 판매 업무를 막지 않는다.

## 5. 첫 사용 버전과 후속 고도화 경계

첫 수입 종단 버전은 M1 → 연결 계약 → M2 → M3 → M4 → M5A/B 최소 → M6A 및 수동 상태 → M7 최소 → M8이다.

5C·6C, 자동 FTA 분석, 항공편 실시간 연동, 다창고, 전체 판매 채널 동기화, 자동 OCR는 첫 완료 조건이 아니다. 국내 매입의 판매 실험은 M5A와 M7/M8 최소 기능으로 먼저 진행할 수 있다. 실제 수입의 요건 확인과 필요한 전문가 검토는 기능 개발 순서 때문에 생략하지 않는다.

각 파트는 처음에 조회·입력·검증·다음 단계 인계까지 하나의 작동 흐름으로 구현하고 자동화와 최적화를 나중에 추가한다. 백엔드만 전부 만든 뒤 UI를 몰아서 붙이는 순서로 진행하지 않는다.

## 6. 공동 구현 기준

- 기존 작업 트리와 현재 진행 중 변경을 확인·보존한다. 다른 작업의 미완료를 이 계획의 완료로 선언하지 않는다.
- Spring은 업무 권한과 데이터, Python/Celery는 수집, Flyway는 스키마를 소유한다.
- 각 모듈은 현재 migration 번호 다음에 필요한 변경만 추가한다. 적용된 migration을 수정하지 않는다.
- 소싱 견적·마진·판매 실적은 조직 비공개다. 합배송이나 업체 연결이 다른 거래의 접근 권한을 열지 않는다.
- 미확인 값과 0, 예상과 실제, 관측 시장과 원산지, 모델 동일성과 유사성을 구분한다.
- 단계별로 의미 있는 계산·권한·중복·수량 보존·버전 테스트와 해당 사용자 흐름을 검증한다. 문서 작성만으로 서비스 테스트 통과를 주장하지 않는다.
- 각 단계 완료 시 변경 범위·검증 명령/결과·남은 항목을 `docs/engineering/`의 해당 단계 문서로 기록한다. 운영 적용과 테스트 환경 완료를 구분한다.

## 7. 작업 역할 사용 방법

M0~M9와 `prp-*` 이름은 작업 범위와 책임을 구분하기 위한 역할 식별자다. 현재 저장소나 개인 환경에 설치된 Codex 스킬을 전제하지 않는다. 별도 스킬을 만들기 전에도 이 문서의 입력·산출물·완료 기준만으로 작업할 수 있어야 한다.

향후 자동화 스킬을 추가한다면 저장소에서 버전 관리되는 위치와 설치 절차를 별도 문서에 기록한다. 개인 홈 디렉터리의 절대 경로나 특정 PC에만 있는 파일을 필수 계약으로 사용하지 않는다.

예시 요청:

```text
M0 범위로 현재 회원·권한 결과를 확인하고 1단계 연결 계약부터 정리해줘.
M3 범위로 확정된 후보 모델을 기준으로 국내외 공급처·견적 기능을 구현해줘.
M6 범위로 기존 CASE 접근을 유지하면서 문서 버전과 검토 요청을 추가해줘.
```

역할 이름을 지정해도 전체 로드맵이 자동 실행되지는 않는다. 선택된 업무 범위만 진행하며 이미 완료된 작업은 반복 구현하지 않는다. 외부 문의·실제 발주·송금·배포는 구현 문서와 구분하여 해당 요청의 권한을 따른다.
