# 무역 운영 플랫폼 도메인 정의

- 버전: v1
- 상태: 도메인 기준 초안. 제품 범위는 [TradeGuard Ops PRD](prd.md)와 [통합 로드맵 v2](import-domestic-platform-roadmap-v2.md)에서 구체화됐으며, 이 문서 자체는 구현 완료를 뜻하지 않는다.
- 용도: PRD 작성·유지보수와 제품 요구사항 정리 기준
- 범위: 상품, PI, 송금 계획, CI, FTA, 선적, 보세창고, 통관

## 1. 문서 목적

이 플랫폼은 상품 품목 라인을 기준으로 Proforma Invoice(PI), 송금 계획,
Commercial Invoice(CI), FTA 검토, 선적, 부분 도착, 보세창고 대기 및 통관
검토를 연결하는 무역 운영 플랫폼이다.

단순한 Invoice 첨부 또는 화물 추적 서비스가 아니다. 거래 초기의 상품정보와
송금·Invoice 구성 계획을 실제 CI, 항공편, 도착 화물 및 통관 신고정보와 계속
대조하여 다음 위험을 사전에 발견하는 것이 핵심 목적이다.

- FTA 적용가액 기준 위반
- PI와 CI 간 상품·수량·금액·원산지 불일치
- Invoice 분할·통합 과정의 누락 또는 중복
- 항공편 지연으로 분리 화물이 다시 합쳐지는 문제
- 인증수출자 문구 및 서명 등의 통관서류 누락
- 통관 지연으로 인한 보세창고 비용 증가
- 관세사에게 불완전하거나 잘못된 품목정보 전달

FTA 및 통관 규칙은 국가, 협정, 품목, 수출자 자격과 세관 실무에 따라 달라질
수 있다. 특정 기준금액이나 서류요건을 전역에 하드코딩하지 않고 협정별 규칙으로
관리하며, 자동판정이 불확실한 경우 담당자 또는 관세사의 확인을 요구한다.

## 2. 공통 데이터 원칙

### 2.1 상품 품목 라인을 원자적 관리 단위로 사용한다

FTA, 원산지, 송금, Invoice 분할·통합 및 통관 판단은 문서 전체가 아닌 상품
품목 라인을 기준으로 수행한다.

실제 운영 건은 최소한 PI와 PI 품목정보가 등록된 후 송금·CI·선적 프로세스를
시작해야 한다. 목업이나 데모에서는 샘플 데이터를 사용할 수 있지만 실제 운영에서
CI 또는 선적 단계부터 시작하면 원자적인 상품정보를 알 수 없어 FTA와 통관 검증이
불가능해진다.

최소 PI 품목정보는 다음과 같다.

- Shipper 상품코드 또는 SKU
- 브랜드
- 상품명 및 영문 Description
- 카테고리
- 수량과 단위
- 단가와 금액
- 통화
- 예상 원산지
- 예상 HS Code 또는 품목분류
- FTA 적용 예정 여부
- 색상, 사이즈, 시즌, 모델
- 필요한 경우 생산 Batch 또는 Lot
- 제조자 정보가 필요한 경우 제조자

### 2.2 SKU와 원산지를 일대일 관계로 간주하지 않는다

동일 SKU라도 다음 조건에 따라 원산지가 달라질 수 있다.

- 색상 또는 Variant
- 시즌
- 생산시기
- 생산공장
- Batch 또는 Lot
- 실제 출고분

SKU는 상품 식별자일 뿐이며, 원산지는 실제 거래 및 출고 품목 라인의 속성으로
관리한다. 가장 작은 실질적 관리 단위는 다음에 가깝다.

`SKU + Variant + Season + Batch/Lot + 원산지 구분`

모든 속성을 모든 상품에 필수로 요구하지는 않는다. 원산지를 구분하는 데 필요한
속성만 조건부 필수로 한다.

동일 SKU에 복수 원산지가 존재하면 원산지별로 별도 품목 라인을 생성해야 한다.
원산지별 수량과 금액을 구분할 수 없는 경우 FTA 적용 및 통관 확정을 제한한다.

### 2.3 단계별 데이터를 덮어쓰지 않는다

다음 데이터는 각각 별도의 스냅샷으로 보존한다.

- 상품 마스터의 기준정보
- PI의 예상 품목정보
- 승인된 송금 및 Invoice 구성 계획
- CI의 실제 품목정보
- Packing List의 포장정보
- 원산지 증빙으로 확인된 정보
- 관세사가 확인한 통관 확정정보

CI의 원산지가 PI와 다르다고 PI 원본이나 상품 마스터를 덮어쓰지 않는다. 계획값과
실제값을 모두 보존하고 차이를 기록한다.

### 2.4 PI와 CI는 다대다 관계다

다음 관계를 모두 지원해야 한다.

- PI 1건 → CI 1건
- PI 1건 → CI 여러 건
- PI 여러 건 → CI 1건
- PI 여러 건 → CI 여러 건
- CI 1건 → HAWB 여러 건
- CI 여러 건 → HAWB 1건
- 동일 PI 또는 CI가 여러 항공편으로 부분 선적

PI와 CI 사이에는 품목 라인별 배정 관계를 둔다. 각 배정 관계는 다음을 포함한다.

- 배정 수량
- 배정 금액
- 통화
- FTA 적용 예정 금액
- FTA 미적용 예정 금액
- 실제 FTA 적용 금액
- 분할 또는 통합 사유
- 원산지 변경 여부
- 계획 대비 차이

### 2.5 내부관리번호를 문서번호와 분리한다

Invoice 번호나 HAWB 번호를 내부관리번호로 사용하지 않는다.

권장 계층은 다음과 같다.

- 거래 내부관리번호
  - PI 등록 또는 FTA·송금 계획 생성 시 발급
  - 원거래 전체를 추적
- 선적 또는 Consolidation 내부관리번호
  - 실제 선적 구성 생성 시 발급
  - 여러 거래의 화물이 하나의 선적에 포함될 수 있음
- 하위 송금, CI, Package, HAWB 식별번호
  - 거래 및 선적 내부관리번호와 연결

### 2.6 최초 사용자와 건별 외부 참여

최초 주요 사용자는 화주다. 초기 제품은 화주가 자신의 거래와 연결된 무역 운영
업무를 관리하는 것을 중심으로 한다.

포워더와 관세사는 별도의 업무 프로그램이 없는 경우에도 화주의 개별 건에
참여(join)하여 해당 건의 업무를 함께 처리할 수 있어야 한다. 포워더와 관세사에
동일한 건별 참여 원칙을 적용한다.

- 외부 참여 권한은 참여가 허용된 개별 건에 부여한다.
- 건에 참여했다는 이유로 화주 조직 전체나 다른 건에 대한 접근 권한을 부여하지 않는다.
- 해당 건에서 조회·등록·수정·검토할 수 있는 범위는 참여 역할과 권한으로 구분한다.
- 초기 범위에는 포워더·관세사가 여러 화주와 전체 업무를 통합 관리하는 전용
  프로세스를 포함하지 않는다.
- 향후 포워더·관세사용 전체 업무 관리 기능을 추가할 수 있도록 사용자·조직의
  소속 관계와 개별 건의 참여 관계를 구분한다.

여기서 참여 대상인 '건'을 거래 단위로 둘지 선적 단위로 둘지, 연결된 문서와
하위 건까지 권한을 어떻게 적용할지는 PRD에서 확정한다. 여러 거래가 하나의
선적에 포함되더라도 다른 거래의 정보가 자동으로 공개되어서는 안 된다.

외부 참여자는 화주 조직의 직원으로 등록하지 않는다. 화주 OWNER·ADMIN이 업체의
담당자 이메일을 복수로 등록하고, 개별 건에 초대할 담당자를 지정한다. 담당자는
이메일 링크로 인증한 후 참여한 건의 권한으로 접속한다. 업체 연락처 등록 자체가
기존 모든 건의 접근 권한을 부여하지는 않는다.

신규 화주 조직의 최초 OWNER는 시스템관리자가 조직 개설 신청을 승인한 후
부여한다. 이후 조직 내부의 ADMIN 지정·해제는 OWNER가 담당한다. 시스템관리자
권한은 조직 역할과 별도로 관리한다.

상세 데이터 모델, 업체별 최대 3명이라는 제안 기본값, 승인 페이지 및 단계별
구현 범위는 [가입 승인 및 참여 권한 설계](identity-access-approval-design-v1.md)를
따른다. 시스템 권한·인증 기반과 가입 승인 백엔드는 1·2단계에서 구현·검증되었다.
승인 화면과 인증 통합은 [3단계](../engineering/identity-stage-3.md)에서 구현·검증되었다.
조직 직원 권한은 [4단계](../engineering/identity-stage-4.md)에서 구현·검증되었다.
외부 업체·건별 이메일 참여는 [5단계](../engineering/identity-stage-5.md)에서 구현·검증되었다.
초기 외부 권한은 운송 정보·문서번호 조회 및 허용된 문서번호 추가이며, 추가 업무 권한과
실제 운영 설정은 후속 단계에서 확정한다.

## 3. 송금 및 Invoice 구성 계획 단계

### 3.1 단계 목적

송금 단계에서는 PI의 상품, 금액, 원산지 및 FTA 조건을 확인하여 송금 회차,
CI 구성과 선적 회차를 사전에 계획한다.

Invoice 분할·통합은 CI 발행 후의 사후조치가 아니라 송금 전후에 Shipper와
협의하여 확정하는 거래 계획이다.

`PI 등록 → 품목 검토 → FTA/운임 검토 → 송금·Invoice 구성 계획 → Shipper 요청 → Shipper 승인 → 송금 → 입금 확인 → CI 발행`

### 3.2 PI를 여러 CI로 분할하는 경우

하나의 PI가 다음 이유로 여러 CI와 선적 건으로 나뉠 수 있다.

- FTA 적용가액 기준 충족
- 원산지 또는 품목 구분
- 선적 일정 분리
- 특정 브랜드 또는 인증 적용 범위 구분
- 기타 통관 또는 거래 조건

특정 기준금액을 CI 총액에 일률적으로 적용해서는 안 된다. 예를 들어 일부
협정에서는 비인증 수출자의 원산지 문구 작성 가능 여부가 개별 Invoice 총액이
아니라 consignment 내 협정상 원산지 상품의 총가액을 기준으로 판단될 수 있다.

다음 금액을 분리해서 관리한다.

- CI 전체 금액
- FTA 적용 가능 후보 금액
- 실제 FTA 적용 신청 금액
- FTA 미적용 금액
- FTA 적용 여부가 확인되지 않은 금액

예를 들어 하나의 CI가 다음과 같이 구성될 수 있다.

- CI 총액: EUR 15,999
- FTA 적용 신청 대상 원산지 상품: EUR 5,999
- FTA 미적용 상품: EUR 10,000

전체 CI 금액만으로 FTA 기준 초과를 판정하지 않는다. 선택된 협정의 규칙에 따라
FTA 적용 대상 원산지 상품가액을 산정한다.

### 3.3 여러 PI를 하나의 CI로 통합하는 경우

여러 PI가 지나치게 소량으로 나뉘어 개별 선적 시 운임이 커질 경우, FTA 적용
가능 범위 안에서 복수 PI를 하나의 CI로 통합할 수 있다.

다음 경우 통합 가능성이 커질 수 있다.

- Shipper가 인증수출자 또는 등록수출자 자격을 보유
- 건별 가액 제한 대신 인증 범위 전체에 대한 원산지 문구 작성 가능
- 특정 브랜드 또는 품목이 인증 범위에 포함
- 운임 최적화를 위해 소량 거래를 합배송

Shipper의 인증번호 보유 여부만으로 자동 통합을 승인하지 않는다. 인증이 특정
브랜드, 품목, 사업장 또는 유효기간에 한정될 수 있기 때문이다.

### 3.4 Shipper FTA 프로필

Shipper 등록 시 다음 정보를 관리한다.

- 인증수출자 또는 등록수출자 여부
- 인증번호
- 발급기관
- 유효기간
- 적용 협정
- 적용 범위
  - 전체
  - 특정 브랜드
  - 특정 품목
  - 특정 사업장
  - 기타 조건부
- 적용 브랜드 또는 품목
- 증빙 문서
- 최근 확인일
- 확인 담당자
- CI 통합 가능성
- 평균 문서 정정 응답시간
- 주 담당자 및 대체 연락처

초기 버전에서는 브랜드·품목별 법적 규칙을 모두 자동 판정하지 않아도 된다.
시스템은 관련 정보를 보여주고, 조건부 적용 시 경고한 뒤 담당자가 근거와 함께
확인하도록 한다.

### 3.5 송금 및 Invoice 구성 계획

PI 품목 라인을 하나 이상의 예정 송금, CI 및 선적 회차에 배정할 수 있어야 한다.

계획 항목은 다음과 같다.

- PI 및 PI 품목 라인
- 예정 송금 회차와 금액
- 예정 CI
- 예정 선적 회차
- 배정 수량 및 금액
- 예상 원산지
- 적용 협정
- FTA 적용 예정 금액
- FTA 미적용 예정 금액
- 분할 또는 통합 사유
- Shipper 요청일
- Shipper 승인 상태
- 승인 증빙
- 계획 버전

### 3.6 Shipper 승인과 버전 관리

Invoice 분할·통합 요청은 단순 메모가 아니라 승인 객체로 관리한다.

`작성 중 → Shipper 요청 → 수정 요청 → Shipper 승인 → 송금 승인 → 송금 완료 → CI 발행`

Shipper 승인 이후 다음 내용이 변경되면 재승인을 요구한다.

- CI별 상품 구성
- 수량 또는 금액
- FTA 적용·미적용 구분
- 원산지
- 통화
- 적용 협정
- Shipper
- 송금 배분
- 선적 구성

이메일이나 외부 메신저에서 승인을 받은 경우 담당자가 승인 근거 파일과 승인 시점을
대신 등록할 수 있어야 한다.

### 3.7 금액·수량 보존 검증

분할·통합 과정에서 다음을 자동 검사한다.

- PI 총수량과 CI 배정수량 합계
- PI 총금액과 송금·CI 배정금액 합계
- 미배정 수량과 금액
- 중복 배정된 수량과 금액
- 통화 불일치
- FTA 적용·미적용 금액 합계
- 송금액과 최종 CI 금액의 차이

### 3.8 송금 단계의 통제 게이트

다음 상태에서는 송금 또는 다음 단계 진행을 제한하거나 재검토를 요구한다.

- PI 품목정보가 불충분
- 원산지별 수량 또는 금액을 구분할 수 없음
- FTA 적용 계획의 근거가 없음
- 인증수출자 자격 또는 적용 범위가 확인되지 않음
- Invoice 분할·통합 계획에 미배정 또는 중복이 있음
- Shipper 승인이 필요한데 승인되지 않음
- 승인 이후 구성내용이 변경됨

## 4. CI 수신 및 PI–CI 대조 단계

### 4.1 CI는 실제정보 확인 지점이다

PI는 예상정보이며 CI는 실제 선적 및 통관에 사용되는 정보다. CI가 발행되면 PI와
승인된 송금·Invoice 구성 계획을 품목 라인 단위로 대조해야 한다.

대조 완료 전에는 CI를 정상 통관용 문서로 확정하지 않는다.

### 4.2 품목별 대조 항목

- SKU 또는 상품코드
- 브랜드
- 상품명과 Description
- 색상, 사이즈, 시즌, 모델
- 수량과 단위
- 단가와 금액
- 통화
- 원산지
- HS Code
- FTA 적용 여부
- Shipper 및 제조자
- 계획 CI와 실제 CI 구성
- 예정 송금과 CI 금액
- 예정 선적 회차

대조 결과 상태는 다음과 같이 구분할 수 있다.

- 일치
- 경미한 차이
- FTA 영향 차이
- 중대한 차이
- 판독 불가
- 재검토 필요

### 4.3 원산지 변경

다음 세 가지 원산지를 분리한다.

- PI 예상 원산지
- CI 기재 원산지
- 증빙 및 관세사 검토로 확인된 최종 특혜 원산지

국가가 EU라는 사실만으로 자동으로 FTA 적용 가능하다고 판단하지 않는다. 실제
협정, 품목별 원산지 기준과 증빙 적합성을 확인해야 한다.

#### EU 원산지 예상 → 비EU 원산지 실제

가능한 영향:

- 예정했던 FTA 적용 불가
- 관세비용 증가
- 이미 분할한 선적의 추가 운임 발생
- 선적 분할의 경제적 효과 상실

시스템 처리:

- FTA 계획 재계산
- 예상 관세 및 비용변화 표시
- 계획 대비 비용 손실 기록
- FTA 미적용 진행 또는 CI 정정 요청
- 담당자와 관세사 확인

#### 비EU 원산지 예상 → EU 원산지 실제

가능한 영향:

- 새로 FTA 적용 가능 후보가 됨
- 기존 FTA 대상가액과 합산 시 가액 기준 초과
- 승인된 Invoice 및 선적 분할 계획이 무효화될 수 있음

시스템 처리:

- 해당 CI만이 아니라 연결된 PI, 다른 CI 및 선적 건 전체 재계산
- FTA 적용 가능 후보 금액과 실제 신청 예정 금액 구분
- 인증수출자 자격 또는 다른 증빙방식 확인
- CI 정정, FTA 미적용 진행 또는 재분할 판단
- 문제 해결 전 선적 또는 통관 확정 차단

원산지 변경은 금액과 관계없이 최소 `FTA 영향 차이`로 분류한다.

### 4.4 관련 거래 전체 재판정

CI 한 건의 원산지, 금액 또는 FTA 적용 여부가 바뀌면 해당 CI만 검사하지 않는다.

다음 범위를 재계산한다.

- 동일 PI에서 파생된 다른 CI
- 같은 송금·Invoice 구성 계획
- 같은 FTA 관리 그룹
- 동일 또는 인접 항공편의 관련 화물
- 동일 Shipper의 다른 거래
- 동일 importer 또는 consignee의 관련 거래
- 동일 MAWB 또는 consolidation 후보
- 동일 통관 일정에 포함될 가능성이 있는 거래

기존 승인의 전제가 달라지면 상태를 `재승인 필요`로 변경한다.

## 5. CI 문서 형식 및 원산지 문구 검증

### 5.1 기본 전달 흐름

일반적인 흐름은 다음과 같다.

`Shipper → 포워더 → 화주 검토 → 관세사 → 통관 신고`

포워더가 Shipper로부터 CI를 수신하면 화주 또는 관세사에게 정상 통관용으로
전달하기 전에 자동 사전검증을 수행한다.

이상이 있는 문서는 공유할 수 있으나 `통관 사용 불가`, `정정 대기` 또는
`검토 필요` 상태를 명확히 표시한다.

### 5.2 검증 항목

선택된 협정과 Shipper 자격에 따라 다음을 검사한다.

- Invoice 번호
- 발행일
- Shipper/exporter 정보
- Consignee/importer 정보
- 품목, 수량, 단가, 금액 및 통화
- 원산지
- HS Code 또는 품목분류
- 일반 FTA 또는 원산지 선언문구
- 인증수출자 전용 문구
- 인증수출자 번호
- 선언문의 필수 장소 및 일자
- 업체 도장
- 서명
- 서명자 또는 담당자 이름
- Packing List 등 관련 문서
- 문구가 적용되는 품목 범위

도장, 서명 및 담당자 이름의 필수 여부를 전역 규칙으로 고정하지 않는다. 적용
협정, 수출국, 인증 유형, 전자문서 인정 여부, 관세사 또는 세관의 추가 요구에 따라
규칙을 구성한다.

규칙 적용 우선순위 예시:

`협정/국가 규칙 → Shipper 자격 → 화주 요구 → 관세사 추가요건 → 거래별 예외`

### 5.3 자동 판독 결과

문구, 도장, 서명 및 담당자 이름 검출 결과는 다음과 같이 표시한다.

- 확인됨
- 누락 의심
- 판독 불가
- 규칙 확인 필요
- 담당자 확인 완료

이미지에서 도장이나 서명의 존재 여부는 탐지할 수 있지만 진위를 자동 보장하지
않는다. 스캔 품질이 낮거나 확신도가 낮으면 사람의 확인을 요구한다.

시스템이 Shipper 문서에 원산지 문구, 인증번호, 도장 또는 서명을 임의로 추가해서는
안 된다. 누락을 탐지하고 정정 요청을 생성한 후 Shipper의 정식 수정본을 받아야 한다.

### 5.4 수정본과 버전 관리

수정 CI가 도착해도 기존 문서를 덮어쓰지 않는다.

각 버전에 다음을 기록한다.

- 버전번호
- 수신일
- 발신자
- 발견된 누락 또는 불일치
- 정정 요청일
- 요청자
- Shipper 회신일
- 변경된 항목
- 재검증 결과
- 화주 승인자
- 관세사 전달일
- 실제 통관에 사용된 버전

## 6. 선적, 부분 도착 및 FTA 재결합 위험

### 6.1 거래·물리·통관 구성을 분리한다

다음 세 구성은 별개로 관리한다.

- 거래상 구성: PI, 송금, CI
- 물리적 구성: Packing List, 박스, 항공편, HAWB, MAWB
- 통관상 구성: Consignment, 신고 묶음, FTA 적용가액

하나의 PI 또는 CI가 복수 박스와 항공편으로 부분 선적될 수 있고, 지연이나
재예약으로 다른 거래 화물과 다시 합쳐질 수 있다.

### 6.2 Package/Carton 관리

Packing List가 확정되거나 partial shipment가 발생하면 박스와 품목의 연결을
관리한다.

박스별 정보:

- Shipper
- PI 및 CI
- Packing List
- 박스 또는 Carton 번호
- 포함 SKU와 수량
- 품목별 원산지
- 품목별 금액 배정
- FTA 적용 예정 금액
- HAWB 및 MAWB
- 예정 항공편
- 실제 항공편
- 출발 및 도착 시점
- 보세창고 반입·반출 시점
- 통관 대기 사유

박스별 내용물을 알 수 없으면 `내용물 미확정`으로 표시하고 FTA 자동판정 신뢰도를
낮추며 필요 시 통관 확정을 제한한다.

### 6.3 항공편 지연과 화물 재결합

FTA 기준을 고려해 분리한 CI 또는 화물이 항공편 지연, 결항 또는 재예약으로 동일
항공편이나 통관 건에 다시 포함될 수 있다.

예시:

- PI-A를 CI-A1과 CI-A2로 분리
- CI-A1 화물이 먼저 출발했으나 지연
- CI-A2가 다음 항공편에 예약
- 지연된 CI-A1이 CI-A2 또는 동일 Shipper의 다른 거래와 같은 항공편에 탑재
- 동일 MAWB, consolidation 또는 통관 건으로 묶일 가능성 발생
- FTA 적용 대상 원산지 상품가액 재합산 필요

같은 항공편만으로 법적 동일 consignment라고 자동 확정하지는 않는다. 다만 강한
위험 신호로 취급하고 포워더 또는 관세사가 확인한다.

### 6.4 교차 거래 위험 탐색

검사 범위를 동일 PI에 한정하지 않는다. 다음 항목이 여러 개 일치하면 합산 위험
후보로 분류한다.

- 동일 Shipper/exporter
- 동일 importer/consignee
- 동일 FTA 협정
- 동일 출발·도착 국가
- 동일 항공편
- 동일 MAWB 또는 consolidation
- ETD 또는 ETA가 지정 시간범위 안에 겹침
- 동일 보세창고
- 동일 통관 예정일
- 동일 신고 건으로 묶일 가능성
- 동일 PI에서 분할된 CI
- FTA 적용 대상 원산지 상품가액의 합계가 협정 기준을 초과할 가능성

### 6.5 재검사 이벤트

다음 이벤트가 발생할 때 FTA 및 통관 위험을 다시 검사한다.

- 항공편 예약
- ETD 또는 ETA 변경
- 지연, 결항 또는 롤오버
- 항공편 재예약
- HAWB 또는 MAWB 변경
- consolidation 변경
- 일부 박스만 출고 또는 도착
- 보세창고 반입
- CI 추가, 삭제 또는 금액 변경
- 품목 원산지 변경
- 통관 신고 그룹 변경

## 7. 보세창고 대기와 비용 위험

### 7.1 Partial arrival 관리

동일 PI의 일부 박스만 먼저 도착하면 먼저 도착한 화물이 보세창고에서 후속 화물을
기다릴 수 있다.

`부분 도착 → 보세 반입 → Free Time 계산 → 후속 화물 ETA 비교 → 대기 또는 부분통관 결정`

관리 항목:

- 보세창고
- 반입시각
- 무료 보관기간
- Free Time 종료 예정일
- 보관료 요율
- 현재 누적비용
- 후속 화물 ETA
- 대기 시 예상 추가비용
- 부분통관 가능 여부
- 대기 또는 부분통관 결정
- 결정자 및 사유

### 7.2 비용과 FTA 위험을 함께 표시한다

포워더가 다음 선택지를 비교할 수 있도록 한다.

- 먼저 도착한 박스 부분통관
- 후속 화물 도착까지 대기
- 후속 화물 항공편 변경
- 다른 거래와 MAWB 또는 consolidation 분리
- FTA 미적용 진행
- 인증수출자 자격 또는 대체 원산지 증빙 확인

화면에는 최소한 다음 두 위험을 함께 표시한다.

- 비용 위험: 보세창고 대기료, 추가 운임
- FTA 위험: 다른 거래 또는 화물과 합산될 경우 적용가액 기준 초과

## 8. 문서 정정 지연과 에스컬레이션

CI에 인증수출자 문구, 일반 FTA 문구, 도장, 서명 또는 담당자 이름이 누락되면
Shipper로부터 수정본을 받아야 통관이 진행될 수 있다.

Shipper의 회신이 늦으면 통관 지연과 보세창고 비용이 발생할 수 있으므로 문서
정정업무를 비용 위험과 연결한다.

`누락 발견 → Shipper 정정 요청 → 예상 응답시간 계산 → 화물 ETA/도착상태 확인 → Free Time과 비교 → 비용경고 → 에스컬레이션`

에스컬레이션 예시:

1. Shipper 주 담당자에게 정정 요청
2. 설정시간 동안 미응답 시 대체 담당자 참조
3. 화주와 포워더 운영책임자 알림
4. 관세사에게 대체 증빙 또는 진행 가능 여부 확인
5. Free Time 임박 시 긴급상태 전환

Shipper별 평균 정정 응답시간과 반복 누락항목을 기록한다. 과거에 특정 누락이
허용되었다는 사실을 현재 규칙의 자동 면제 근거로 사용하지 않는다.

## 9. 관세사 검토 및 통관 확정

### 9.1 관세사에게 전달할 품목정보

관세사는 CI 전체가 아니라 품목 라인 단위로 다음을 검토할 수 있어야 한다.

- 최종 신고 품명
- 카테고리
- HS Code
- 수량 및 단위
- 단가와 신고가액
- 원산지
- 적용 세율
- FTA 적용 여부
- FTA 적용가액
- 원산지 문구와 증빙 적합성
- 인증, 검역 또는 기타 신고요건
- PI와 CI의 차이
- 담당자 검토 의견

관세사가 확정한 값은 PI 또는 CI 원본을 덮어쓰지 않고 별도의 통관 확정값으로
보존한다.

### 9.2 통관 전달 게이트

다음 항목이 완료되어야 정상 통관용으로 관세사에게 전달할 수 있다.

- PI–CI 품목 대조
- 수량과 금액 배정 검증
- 원산지 변경 검토
- FTA 적용가액 재계산
- 인증수출자 자격과 적용 범위 확인
- 필수 원산지 문구 확인
- 필요한 도장, 서명 및 담당자 이름 확인
- Packing List와 박스정보 확인
- 관련 선적의 합산 위험 검토
- 수정본이 있는 경우 최종 버전 확정

문제가 있는 문서는 관세사에게 참고용으로 공유할 수 있으나 `정정 대기`,
`FTA 재검토`, `통관 사용 불가` 등의 상태를 명확하게 표시한다.

## 10. 주요 자동 경고 및 차단 조건

다음 조건에서는 경고 또는 확정 차단을 고려한다.

- PI 없이 실제 운영 프로세스를 시작
- PI 품목정보가 불충분
- 동일 SKU의 복수 원산지를 구분할 수 없음
- PI 수량·금액과 CI 배정 합계 불일치
- 송금 계획과 CI 금액 불일치
- PI와 CI의 원산지 변경
- HS Code 또는 카테고리 변경
- 인증수출자 자격 또는 적용 범위 미확인
- FTA 적용 대상가액 기준 초과 가능
- 항공편 변경으로 분리 화물이 다시 합쳐질 가능성
- 동일 Shipper의 다른 거래와 동일 MAWB 또는 통관 건으로 묶일 가능성
- 박스별 품목·원산지·금액 배정 불명확
- 필수 원산지 문구 누락
- 인증수출자 번호 누락
- 필요한 도장, 서명 또는 담당자 이름 누락
- CI 정정 대기시간이 보세창고 Free Time을 초과할 가능성
- 승인된 송금·Invoice·선적 계획이 사후 변경됨

차단 강도는 다음을 고려해 설정한다.

- 단순 주의
- 담당자 확인 필요
- 관세사 확인 필요
- 권한자 예외 승인 필요
- 선적 확정 차단
- 통관 전달 차단

## 12. PRD 작성·유지보수 지침

이 도메인의 PRD를 작성하거나 갱신할 때 다음 원칙을 적용한다.

1. 기능을 문서 단위가 아니라 상품 품목 라인 단위로 설계한다.
2. 상품 마스터와 거래별 품목 스냅샷을 구분한다.
3. PI 등록을 실제 운영 프로세스의 최소 시작점으로 둔다.
4. PI–CI 및 CI–선적 관계를 일대일로 가정하지 않는다.
5. 계획값과 실제값을 분리한다.
6. 원산지 변경 시 관련 거래 전체를 재판정한다.
7. 전체 Invoice 금액과 FTA 적용 대상 원산지 상품가액을 구분한다.
8. 특정 기준금액을 전역에 하드코딩하지 않는다.
9. 항공편 지연과 partial shipment를 FTA 및 비용 위험과 연결한다.
10. CI 문구와 서명 검증을 통관 전 필수 게이트로 고려한다.
11. 자동판정이 법적 결론을 대신하지 않도록 담당자와 관세사 확인 절차를 둔다.
12. 수정본과 승인 이력을 덮어쓰지 않고 버전으로 보존한다.
13. MVP 필수 통제와 후속 자동화 기능을 구분한다.
14. 최초 사용자인 화주를 중심으로 설계하고, 포워더·관세사의 권한은 참여한 건의
    범위로 제한한다.
15. 조직 소속과 건별 참여를 구분하여 향후 외부 참여자의 전체 업무 관리 기능으로
    확장할 수 있도록 한다.

### 12.1 MVP에 포함할 핵심

- 화주 중심의 업무 관리와 포워더·관세사의 건별 참여 및 권한 관리
- PI 및 PI 품목 등록
- PI 품목의 예상 원산지와 금액
- 동일 SKU의 복수 원산지 지원

- Shipper 승인 이력
- PI–CI 품목 대조
- 원산지 및 금액 변경 탐지
- FTA 적용 가능 후보가액과 실제 신청금액 구분
- CI 필수문구 및 서명정보 검증
- CI 수정본 버전 관리
- 항공편 지연 및 partial shipment 상태
- 관련 화물의 FTA 합산 위험 경고

## 13. PRD에서 별도로 확인해야 할 미결정 사항

- Shipper 승인 방식

## 14. 법률·규정 적용 주의사항

이 문서는 제품 설계를 위한 도메인 초안이며 법률 또는 관세 자문을 대신하지 않는다.
실제 FTA 적용 여부, 기준가액, consignment 범위, 원산지 선언문구, 서명 요건 및
증빙방식은 해당 거래에 적용되는 협정과 관세사의 확인을 거쳐야 한다.

시스템은 다음 역할을 수행한다.

- 적용 가능한 규칙 후보 제시
- 데이터 및 문서 누락 탐지
- 변경으로 인한 재검토 필요성 탐지
- 담당자와 관세사의 검토 및 승인 기록
- 비용과 일정 위험의 조기 경고

시스템이 담당자 또는 관세사의 법적 판단을 임의로 대체해서는 안 된다.
