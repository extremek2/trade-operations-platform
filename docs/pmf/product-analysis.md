# 제품 분석 · PMF 진단 — 단일 파일판

## 목적

그럴듯한 문서를 만드는 것이 아니라 사용자가 무엇을 아직 모르는지 드러낸다. 확인한 사실,
기억은 있지만 기록이 없는 말, 아직 검증하지 않은 짐작을 절대 섞지 않는다.

이 파일만으로 전 과정을 수행한다. 다른 스크립트·참조·템플릿을 찾지 않는다. Codex가 코드와
배포물을 직접 조사하고, 사용자와 문답하고, 결과 파일을 직접 작성한다.

## 결과 경로

모든 디렉터리는 없으면 만든다.

```text
~/Downloads/AI마케팅실습/
├── 07_제품분석/
│   ├── answers.json
│   ├── evidence.json
│   ├── pmf_input.json
│   ├── pmf.json
│   ├── pmf_report.md
│   ├── assumptions.md
│   └── analysis.html
└── 01_내비즈니스/
    └── icp.json
```

## 절대 규칙

1. 제품을 먼저 본다. 코드나 화면에서 알 수 있는 것을 사용자에게 묻지 않는다.
2. 화면에서 알 수 없는 항목만 한 번에 하나씩 묻는다.
3. 확신 판정이 필요한 답은 사용자가 직접 1 확인 / 2 미기록 / 3 짐작 중 고른다.
4. `확인`이면 실제 출처를 한 번 더 묻는다. 출처가 모호하면 그대로 기록하고 꾸미지 않는다.
5. PMF는 설명이 아니라 실제로 존재하는 근거 파일만 통과시킨다.
6. 앞 PMF 단계가 미통과면 뒤 단계는 묻지 않는다.
7. 모르는 답은 `모름`으로 보존한다. 빈칸을 대신 추측하지 않는다.
8. 기존 결과가 있으면 먼저 읽고, 다른 제품의 데이터가 섞였는지 확인한다.
9. 사용자 승인 없이 외부 시스템을 수정하거나 고객에게 연락하지 않는다.

## 1단계 — 제품을 직접 본다

작업 폴더와 사용자가 준 배포 URL을 조사한다. 가능한 경우 다음을 읽는다.

| 대상 | 확인할 내용 |
|---|---|
| README, docs | 제품 정의, 해결하려는 문제, 현재 단계 |
| package.json, pyproject.toml | 프로젝트 이름과 기술 스택 |
| 랜딩·페이지 코드 | 고객 약속, 기능, 가격, CTA |
| 라우트·컴포넌트 | 실제 구현 범위 |
| 배포 URL | 공개 상태, 빈 화면·오류·반응형 상태 |
| 환경변수 예시·결제 코드 | 수익 모델과 외부 서비스 흔적 |
| 테스트·로그 | 검증된 주장과 아직 검증되지 않은 주장 |

소스 코드가 있으면 민감한 `.env` 값은 출력하지 않는다. 배포 화면은 가능하면 데스크톱과 모바일
폭에서 확인한다. 사실과 코드 주석의 계획을 구분한다.

조사 후 아래 형식으로 사용자에게 확인받는다.

```text
코드와 화면을 보니 이렇게 이해했습니다.
제품    : (한 문장)
상태    : (배포 전/후, 실제 동작 범위)
수익모델: (확인된 흔적 또는 안 보임)
맞나요? 틀린 곳만 고쳐 주세요.
```

사용자가 확인하면 이 세 항목은 `확인`으로 기록하고 출처에 파일 경로와 URL을 쓴다.

## 2단계 — 화면에 없는 것을 인터뷰한다: 18개 인터뷰 항목

아래 항목 중 1단계에서 확정되지 않은 것만 묻는다. 한 메시지에 한 질문만 한다.

| 키 | 질문 | 확신 판정 |
|---|---|---|
| 제품한줄 | 무엇을 만들고 있나요? 한 문장으로 | 아니오 |
| 푸는문제 | 고객이 겪는 어떤 불편을 풉니까? 기능이 아니라 고객의 말로 | 예 |
| 지금상태 | 지금 어디까지 만들어졌나요? | 아니오 |
| 고객유형 | 누구에게 팝니까? b2c / b2b / b2g | 아니오 |
| 고객업종 | 첫 고객은 어떤 업종·상황의 사람인가요? | 아니오 |
| 고객규모 | 회사·조직·개인의 규모는 어느 정도인가요? | 아니오 |
| 고객지역 | 어느 지역을 먼저 공략합니까? | 아니오 |
| 고객직책 | 실제로 만나고 결정할 사람의 직책은? B2C면 본인 | 아니오 |
| 아픈지점 | 그 사람이 실제로 할 법한 말로 아픈 점 세 가지는? | 예 |
| 모이는곳 | 구체적인 커뮤니티·협회·행사·매체 이름은? | 예 |
| 현재대안 | 지금은 이 문제를 어떻게 넘기고 있나요? | 예 |
| 경쟁상대 | 같은 문제를 푸는 서비스는? | 아니오 |
| 차별점 | 기존 대안과 무엇이 어떻게 다릅니까? | 예 |
| 한문장 | `[누구]를 위한 [무엇]. [대안]과 달리 [핵심 차이]` | 아니오 |
| 채널 | 첫 고객을 어디서 만날 겁니까? 1~2개만 | 예 |
| 가격 | 얼마를 어떤 방식으로 받을 계획입니까? | 아니오 |
| 지불의향 | 그 값을 내겠다고 말하거나 실제 결제한 사람이 있나요? | 예 |
| 무너지는조건 | 무엇이 틀리면 사업이 무너집니까? 가장 큰 가정 세 가지 | 아니오 |

`푸는문제`와 `아픈지점`은 제품 기능이 아니라 고객의 불편이어야 한다. `모이는곳`은 “온라인”처럼
막연한 답을 받지 말고 검색 가능한 고유명사를 받는다. `현재대안`은 엑셀, 메모장, 직원처럼
서비스가 아닌 것도 포함한다.

### 확신 판정

확신 판정이 `예`인 답을 받은 직후 반드시 묻는다.

```text
이 답의 근거는 어느 수준인가요?
1. 확인했다 — 고객에게 직접 듣거나 데이터로 봄
2. 들은 적은 있지만 기록은 없음
3. 아직 짐작임
```

- 1번이면 “어디서 확인했나요?”를 한 번 더 묻고 파일·사람·URL을 받는다.
- 2번은 `미기록`, 3번은 `짐작`에 넣는다.
- `모름`은 `짐작`에 내용 `모름`으로 넣는다.
- 사용자 대신 등급을 정하지 않는다.

### 확장판

사용자가 확장 분석을 원할 때만 아래를 추가한다.

| 키 | 질문 | 확신 판정 |
|---|---|---|
| 시장크기 | 이 문제를 가진 사람이 대략 몇 명입니까? | 예 |
| 원가 | 고객 한 명당 드는 비용은? | 아니오 |
| 브랜드이름 | 이름과 그 이름을 고른 이유는? | 아니오 |
| 브랜드약속 | 고객에게 하는 약속 한 줄은? | 아니오 |
| 구십일 | 앞으로 90일 안에 반드시 할 것 세 가지는? | 아니오 |

## 답변 저장

`answers.json`을 UTF-8 JSON으로 쓴다.

```json
{
  "제품한줄": "", "푸는문제": "", "지금상태": "",
  "고객유형": "b2c", "고객업종": "", "고객규모": "",
  "고객지역": "", "고객직책": "",
  "아픈지점": "쉼표로 구분", "모이는곳": "쉼표로 구분",
  "현재대안": "", "경쟁상대": "쉼표로 구분",
  "차별점": "", "한문장": "",
  "채널": "쉼표로 구분", "가격": "", "지불의향": "",
  "무너지는조건": "쉼표로 구분",
  "작성일": "YYYY-MM-DD", "확장판": false
}
```

쉼표가 금액의 천 단위 구분자일 수도 있으므로 무조건 분리하지 않는다. 목록으로 받은 항목만
문답에서 구분한 항목 단위로 보존한다.

`evidence.json`은 다음 형식이다.

```json
{
  "확인": [{"항목":"질문 원문","내용":"답","출처":"실제 경로·URL·사람"}],
  "미기록": [{"항목":"질문 원문","내용":"답","출처":""}],
  "짐작": [{"항목":"질문 원문","내용":"답 또는 모름","출처":""}]
}
```

## 3단계 — PMF 진단 인터뷰

네 단계를 앞에서부터 하나씩 묻는다. `그렇다`만으로 통과시키지 않는다.

| 단계 | 이름 | 통과 질문 | 근거 예시 |
|---|---|---|---|
| 1 | 문제-해결 적합 | 문제를 겪는 사람과 직접 이야기했고, 그들이 이미 돈이나 시간을 쓰는가? | 인터뷰 메모, 답장, 통화 기록 |
| 2 | 제품-시장 적합 | 한 번 쓰고 끝나지 않고 계속 돌아와 쓰는 사람이 있는가? | 주차별 재사용 로그 |
| 3 | 시장 진입 적합 | 우연이 아니라 반복적으로 고객을 데려오는 경로가 있는가? | 채널별 유입·전환 기록 |
| 4 | 확장 | 돈이나 시간을 더 넣으면 결과가 비례해 커지는가? | 광고비 대비 유입·매출 기록 |

각 단계에서 `예`라면 근거의 절대 파일 경로를 받는다. 경로가 비었거나 파일이 실제로 없으면
그 단계는 미통과다. 디렉터리나 새로 만든 빈 파일은 근거로 인정하지 않는다. 가능하면 파일을
읽어 해당 주장과 관계있는 내용인지 확인한다. 미통과 즉시 뒤 단계 질문을 멈춘다.

`pmf_input.json`:

```json
[
  {"단계":1,"답":true,"근거경로":"/절대/경로/interviews.md"},
  {"단계":2,"답":false,"근거경로":""}
]
```

도달 단계는 앞에서부터 연속으로 통과한 개수다. 1단계 미통과면 0단계다.

`pmf.json`에는 진단일, `도달단계`, 각 단계의 이름·판정·근거경로·사유, `다음목표`를 쓴다.

`pmf_report.md`는 다음 구조로 쓴다.

```markdown
# PMF 진단 결과
- 진단일: YYYY-MM-DD
- **도달 단계: N단계 / 4단계**

## 단계별
| 단계 | 이름 | 판정 | 근거 |

## 다음에 할 일
(첫 미통과 단계의 질문과 필요한 근거)

## 이 진단을 믿을 수 있는 이유
실제로 존재하는 근거 파일만 통과시켰다는 설명
```

## 가정 목록

`assumptions.md`에 작성일과 `확인 N / 기록없음 N / 짐작 N`을 쓰고 세 그룹을 분리한다.
확인 비율은 `확인 / 전체 근거 항목 × 100`이다. 30% 미만이면 문서와 최종 안내에서
“현재는 가설 버전”이라고 명시한다. 짐작·미기록 목록이 다음 고객 인터뷰 질문이다.

## 고객 발굴용 ICP

`~/Downloads/AI마케팅실습/01_내비즈니스/icp.json`:

```json
{
  "고객유형":"", "업종":"", "규모":"", "지역":"", "직책":"",
  "겪는문제":"", "검색가능한특징":[], "제외조건":[],
  "제품한줄":"", "작성일":"YYYY-MM-DD", "검색쿼리":[],
  "만든스킬":"product-analysis"
}
```

검색쿼리는 고정 문구를 기계적으로 붙이지 않는다. 고객이 모이는 구체적 장소, 문제를 표현한
말, 업종·지역·직책을 조합해 실제 검색 가능한 6~10개 문장으로 만든다. B2C는 문제 후기와
커뮤니티, B2B는 협회·회원사·전시회, B2G는 기관·부서·공고 중심이다.

기존 `icp.json`이 다른 제품 데이터라면 덮어쓰기 전에 `icp.이전.json`으로 보존한다.

## 단일 HTML 전략 문서

`analysis.html`은 외부 파일 없이 열리는 완결된 UTF-8 HTML이다. CSS는 `<style>`에 내장한다.
웹폰트는 선택 사항이며 없어도 레이아웃과 내용이 유지되어야 한다. 반응형이고 인쇄 가능해야 한다.

문서는 다음 10개 챕터를 모두 포함한다.

1. 요약 — 제품 한 줄, PMF 단계, 다음 한 행동
2. 무엇을 만들고 있나 — 문제, 제품, 현재 상태
3. 누가 쓰나 — 유형, 업종·상황, 규모, 지역, 직책, 아픈 지점, 모이는 곳
4. 지금 어떻게 해결하나 — 현재 대안과 경쟁자
5. 왜 우리인가 — 차별점과 포지셔닝 문장
6. PMF 진단 — 4단계 표, 현재 단계, 미통과 이유와 필요한 근거
7. 어떻게 알릴 것인가 — 선택한 1~2개 채널
8. 돈은 어떻게 버나 — 가격과 지불 의향
9. 무엇이 틀릴 수 있나 — 무너지는 조건 세 가지
10. 근거와 가정 — 확인·미기록·짐작을 시각적으로 분리

### HTML 품질 기준

- 상단에 제목, 작성일, PMF 단계, 목차를 둔다.
- 카드·표·태그를 사용하되 사실과 가정을 색·라벨로 구분한다.
- 좁은 화면에서 가로 스크롤 없이 읽힌다.
- 모든 사용자 입력은 HTML 이스케이프한다.
- 빈 값을 그럴듯한 문장으로 채우지 말고 `모름` 또는 `확인 필요`로 표시한다.
- PMF 단계와 근거 수치는 JSON·Markdown과 일치해야 한다.
- 마지막에 “고객에게 직접 확인한 뒤 다시 실행하면 짐작이 확인으로 이동한다”고 쓴다.

## 완료 검증과 보고

완료 전에 모든 JSON을 다시 파싱하고, 필수 파일이 존재하며 비어 있지 않은지 확인한다.
HTML에 10개 챕터, PMF 단계, 가격, 포지셔닝, 근거 세 그룹이 들어 있는지 검사한다.

사용자에게 한 번에 알린다.

1. PMF 단계와 근거
2. 확인/미기록/짐작 개수와 비율, 확인 30% 미만이면 가설 버전 표시
3. `analysis.html`과 `icp.json`의 클릭 가능한 경로
