## 1. 목적과 범위 결정

상품 후보를 발견하고, 국내 공급 조건과 판매 채널의 근거를 비교한 다음, 실제 판매 결과로 계속 팔 상품을 고르는 개인 운영 모듈을 만든다. 트렌드 수집은 중요한 입력이지만 수집량 자체를 사업 성과로 보지 않는다.

이 모듈을 선택했을 때의 진행 순서는 `국내 판매 검증 → 검증된 상품군의 수입 타당성 검토 → 소량 수입 검증 → 필요에 따른 확장`이다. 이는 플랫폼 전체의 필수 게이트가 아니며 해외 매입 경로는 국내 판매 실적 없이 별도로 시작할 수 있다. 국내 위탁 판매 자체는 수입이 아니다. 수출은 현재 모듈에 포함하지 않으며 수입 이후의 필수 단계로도 정하지 않는다.

일본을 포함한 해외 트렌드는 참고할 수 있지만, 해외 인기와 국내 구매 수요를 구분한다. 국내 도매·위탁 소싱의 수출 가능성이 없다고 단정하지는 않되 초기 수익 계획에는 반영하지 않는다.

기존 무역 운영 도메인 문서는 후속 실제 수입 거래의 기준으로 유지한다. 이 문서는 그 도메인의 전체 MVP를 구현하기 전에 수행할 독립적인 선행 모듈이다. 상품 검증을 시작하기 위해 PI·CI·선적 건을 만들 필요가 없다.

### 포함

- 키워드·콘텐츠·상품 링크의 발견 및 관찰 기록
- 키워드의 구매 문제 해석, 상품군과 판매 후보 연결
- 국내 공급 상품 비교와 공급 조건 확인
- 상품×판매 채널별 수요 근거와 예상 수익 계산
- 수동 판매 등록 후 실험 기간·예산·성과·정산 기록
- 판정 이력 및 후속 수입 검토용 요약

### 제외

- 수출 시장 분석, 해외 판매 등록, 해외 주문·반품 운영
- 수입 발주·결제, PI/CI 자동화, 통관·FTA·물류 운영
- 쇼핑몰 자동 등록·자동 주문·재고 동기화와 ERP 기능
- 전 SNS 실시간 급등 감시, 판매량 추정 모델, 불투명한 종합 추천 점수
- 유료 데이터 구독을 전제로 한 핵심 기능, 무허가 크롤링
- 다중 판매 채널 동시 실험, IR deck 및 투자 유치 기능

## 2. 현재 프로젝트와 차이

2026-09-08 작업 트리에서 처음 확인했고, 2026-09-12 네이버 쇼핑 검색 제거와 V18을 합친 현재 코드·스키마를 다시 대조했다. 백엔드 전체 92개와 Shopping Insight 단위 테스트 3개는 통과했지만 외부 API 키·실응답, 프런트엔드 전체, 브라우저 E2E와 운영 이미지는 다시 검증하지 않았다. 구현 시 최신 작업 트리를 다시 확인하고 기존 변경을 보존한다.

| 현재 자산 / 경로 | 확인한 상태 | 모듈에서의 처리 |
|---|---|---|

네이버 쇼핑 검색 API 종료와 데이터랩 이관은 서로 다른 변화다. 종료된 쇼핑 검색을 새로운 핵심 경로에 넣지 않는다. 기존 데이터는 수집일과 과거 자료 표시를 유지하고 삭제하지 않는다. 외부 서비스 현황 근거는 11절에 정리한다.

## 3. 사용 흐름과 판정

`발굴함 → 상품군 검토 → 판매 후보 → 공급·채널·비용 검토 → 판매 실험 → 판정`

### 3.1 발굴과 상품군 검토

발굴함에 원문 키워드, 출처 URL, 국가, 언어, 관측일, 관측 지표와 단위를 저장한다. 검색 관심·영상 조회·리뷰·상품 순위는 서로 다른 지표로 표시한다. 소스 장애나 지표 미제공은 0으로 저장하지 않는다.

사용자는 다음을 적고 상품군에 연결한다.

1. 누가 어떤 상황에서 이 물건을 구매하는가?
2. 키워드가 어떤 용도와 상품 유형으로 이어지는가?
3. 국내 공급 후보가 있는가? 다른 옵션의 중복 등록은 아닌가?
4. 국내 판매 채널에서 확인할 근거가 있는가?

상품군은 용도에 따른 묶음이며 동일 SKU 묶음인 클러스터와 구분한다. 예를 들어 ‘좁은 공간 수납’에는 서로 다른 모델과 유형이 속할 수 있다. 이는 설명용 예시이며 현재 유행을 확인한 상품군이 아니다.

공급 폭은 비교 상품 3개·공급자 2곳을 우선 찾아보되 부족하면 자동 탈락시키지 않는다. 공급자 집중이나 유일 상품이라는 사실을 기록한다. 원문과 한국어 해석을 함께 남기며 자동 번역 제목만으로 동일 상품을 확정하지 않는다.

### 3.2 공급·채널 검토

- 공급: 공급자, 출고 국가, 거래 유형, 상품·옵션, 공급가, MOQ, 배송비, 출고 소요일, 반품 조건, 재고 확인일, 판매 채널 제한, 상세 이미지 사용 가능 여부와 확인 근거.
- 거래 유형: `CONSIGNMENT / PURCHASE / UNKNOWN`. 플랫폼 이름만으로 위탁 가능성을 확정하지 않는다.
- 상품 일치: 외부 상품 ID, JAN/GTIN, 모델, 옵션을 사용하고 `동일 상품 / 유사 상품 / 미확인`으로 구분한다.
- 채널: URL, 확인일, 채널, 모델·구성, 배송 포함 가격, 광고 여부, 리뷰 날짜·수, 표시된 구매 문구와 기간. 표시되지 않는 값은 미확인이다.
- 근거 등급: `관심 신호 / 대리 신호 / 채널의 구매 표시 / 본인 거래`. 리뷰와 랭킹을 판매량으로 환산하지 않는다.
- 초기 공급 견적이 오래되었으면 실험 시작 전에 재확인한다. 제안 기본 재확인 주기는 7일이며 공급 특성에 따라 조정한다.

### 3.3 상태와 전이 조건

후보 상태는 업무 진행만 표현하고 최종 판단은 별도 이력으로 남긴다.

| 상태 | 진입 조건 / 다음 행동 |
|---|---|
| DISCOVERED | 출처 또는 직접 작성한 가설이 있음 |
| REVIEWING | 상품군과 구매 이유를 기록하고 공급·채널을 조사 |
| READY | 선택 공급 조건·예상 비용 확인, 실험 채널·기간·예산·최대 손실 설정 완료 |
| TESTING | 사용자가 외부 채널에서 직접 등록한 뒤 판매 URL과 시작일 입력 |
| REVIEW_DUE | 기간 또는 예산 도달, 결과 검토가 필요한 상태. 외부 광고·판매가 자동 중단되지는 않음 |
| CLOSED | 판정과 이유 기록. 재실험 시 이전 결과를 보존하고 새 실험 생성 |

중간 보류·제외는 어느 단계에서도 이유와 함께 기록할 수 있다. 실험 중이면 먼저 종료 사유를 남긴다. READY는 인기 보증이나 자동 구매 승인이 아니다.

판정은 `HOLD / STOP / KEEP / SCALE / IMPORT_REVIEW`로 둔다. 데이터 부족은 HOLD, 이익이나 운영 조건이 맞지 않으면 STOP, 반복성 검토가 필요하면 KEEP으로 구분한다. 판정 변경은 이전 값을 덮어쓰지 않고 이력으로 저장한다.

## 4. 예상 수익과 실제 결과

초기 KRW 기준, 주문당 같은 수량·옵션·배송 조건으로 비교한다. 금액은 decimal로 계산하고 수수료의 적용 대상과 반올림 규칙을 저장한다. 미확인 비용을 0으로 간주하지 않으며 예상 비용과 실제 비용은 구분한다.

### 예상 주문 공헌이익

`상품 결제액 + 고객 부담 배송비 - 판매자 부담 할인 - 공급 상품 원가 - 공급·출고 배송비 - 포장비 - 채널·결제 수수료 - 예상 광고비 배분 - 예상 반품·불량 손실`

- 상품 결제액은 판매자 할인을 차감하기 전 기준으로 정의하여 할인 중복 차감을 방지한다.
- 공급가가 개당인지 묶음당인지와 주문 수량을 기록한다. MOQ 사입의 초기 현금 지출은 주문당 원가와 따로 보여준다.
- 무료 배송도 공급처에 지급하는 운송비가 있으면 비용으로 반영한다.
- 예상 반품 손실은 가정임을 표시한다. 실험의 실제 손실과 이중 차감하지 않는다.
- 세금 처리 기준을 명시하고 미확정이면 ‘세무 조정 전 추정’으로 표시한다. 공헌이익을 순이익이라고 부르지 않는다.

계산 예시: 상품 결제액 20,000원, 고객 배송비 0원, 공급 원가 11,000원, 출고 배송비 3,000원, 수수료 2,000원, 광고비 1,000원, 반품 손실 충당 500원, 나머지 0원이라면 예상 주문 공헌이익은 2,500원이다. 이는 가상의 계산 검증용 값이다.

### 실제 실험 결과

실험별·일자별 주문 수, 판매 수량, 취소·반품, 매출, 고객 배송비, 환불액, 원가, 배송비, 수수료, 광고비, 기타 직접 비용을 입력한다. 주문 수와 판매 수량은 분리한다. 기간 총계와 일별 합계를 중복 합산하지 않는다.

실제 실험 공헌이익은 동일 기간의 환불 반영 수입에서 실제 직접 비용을 뺀다. 미정산·미확정 반품 비용이 있으면 잠정 결과로 표시한다. 고정비·본인 노동·세무 조정 전 결과임을 명시한다. 응대·발주 소요시간도 별도 기록해 소득 대비 운영 부담을 검토한다.

전환율은 노출·클릭 등 분모가 실제 제공될 때만 계산한다. 무판매를 `노출 부족 / 클릭 부족 / 전환 부족 / 비용 문제 / 원인 미확인`으로 분리하고, 짧은 무판매만으로 상품군 전체를 실패로 확정하지 않는다.

## 5. 최소 화면

| 화면 | 필요한 정보와 동작 |
|---|---|
| 검증 보드 `/validation` | 이번에 시험할 후보, 상태, 다음 행동, 미확인 비용, 검토 기한. 거대한 트렌드 차트보다 후보 선택을 우선 |
| 발굴함 `/validation/discovery` | 수동 입력·CSV·활성 수집원의 관찰, 국가·출처·날짜, 상품군 연결·보류 |
| 후보 상세 `/validation/candidates/:id` | 구매 가설, 상품군, 공급 비교, 채널 근거, 예상 비용 버전, 판정 이력 |
| 실험 상세 `/validation/experiments/:id` | 채널 URL, 예산·기간, 일별 실적, 잠정·확정 결과, 다음 판정 |

수집 상태는 성공·자료 없음·실패·비활성·한도 도달로 구분한다. 원본 지표를 가져오지 못하면 성공처럼 보이는 샘플 값을 채우지 않는다. 자동 등록·주문 버튼은 만들지 않는다.

## 6. 데이터와 서버 책임

별도 서비스나 DB를 신설하지 않는다. Spring Boot가 업무 데이터와 권한, FastAPI/Celery가 허용된 외부 수집을 담당한다. 스키마 소유권은 기존 Flyway에 둔다. 구현 시 Java 엔티티와 Python 모델을 함께 맞추고 두 서비스가 각자 테이블을 생성하지 않게 한다.

### 논리 데이터 모델

| 객체 | 핵심 필드 / 관계 |
|---|---|
| source_registry | 키, API/RSS/MANUAL, 비용·사용 조건 상태, 허용 목적, 확인일, 보관·갱신 규칙, 호출 예산, 활성 여부. 기존 retail_source 확장 여부를 첫 설계에서 결정 |
| trend_observation | 출처·외부 ID, 국가·언어, 키워드/제목, URL, 관측 시각, 지표·값·단위·대상 기간, 제한된 원본. 상품 ID 없이 저장 가능 |
| product_family | 조직, 이름, 구매 문제, 포함·제외 기준, 원문/번역 별칭 |
| validation_candidate | 조직, 상품군, 가설, 목표 시장 KR, 상태, 생성자, version. observation 연결은 여러 건 허용 |
| candidate_supply | 후보, 기존 wholesale_product 참조(선택), 수동 공급자·상품 링크, 동일성 판정, 거래 유형, 선택 여부, 공급 조건 스냅샷 |
| channel_evidence | 후보, 채널·국가, URL, 관측일, 모델/옵션, 근거 종류, 지표 정의·기간, 사용자 메모 |
| cost_scenario | 후보·공급 조건, 버전, 수량·통화·가격·비용·수수료 기준, 미확인 필드, 계산식 버전 |
| sales_experiment | 후보, 선택 공급·비용 버전, 채널·등록 URL, 시작/종료, 예산·손실 한도, 상태 |
| experiment_daily_result | 실험·영업일, 수량·금액·노출/클릭(선택), 정산 상태. 실험+날짜 유일성 |
| validation_decision | 후보·실험(선택), 판정, 근거, 부족한 자료, 다음 행동, 작성자·시각 |

후보와 관측 자료의 연결에는 연결 테이블을 둔다. 공급 조건과 비용 시나리오를 변경해도 시작된 실험의 기준은 덮어쓰지 않는다. 공급처 가격 변경은 최신 카탈로그를 갱신하되 과거 견적을 보존한다.

기존 source_product와 wholesale_product의 외부 ID 유일성을 재사용한다. 동일 제목·다른 공급자를 합치지 않는다. 기존 retail_popular_product의 제목 유일성 및 누락 지표 0 기본값을 새 시계열 근거 저장에 그대로 적용하지 않는다. 오래된 값의 0/미제공을 구분할 근거가 없으면 해당 한계를 표시한다.

모든 비공개 업무 데이터는 organization_id로 격리한다. OWNER/ADMIN/OPERATOR는 작성, VIEWER는 조회만 허용한다. CASE와 PLATFORM 세션은 조직 업무 접근 권한으로 취급하지 않는다. 서버가 세션에서 조직을 결정하고, 참조하는 후보·실험도 같은 조직인지 검사한다.

### 제안 API와 작업 인터페이스

- `/api/v1/validation/candidates`: 목록·생성·상세·수정, 필터와 페이지 처리
- `/api/v1/validation/families`: 상품군 관리
- `/api/v1/validation/observations`: 수동 관측 등록·조회·후보 연결
- `/api/v1/validation/candidates/{id}/supplies`, `/evidence`, `/cost-scenarios`, `/decisions`: 후보 하위 자료
- `/api/v1/validation/experiments`: 실험 생성·조회, `/{id}/start`, `/{id}/finish`, `/{id}/daily-results`
- `/api/v1/validation/imports`: CSV 미리보기·확정. 행 오류, 중복, 가져오기 ID 반환
- `/api/v1/validation/collection-jobs`: 서버가 허용한 소스 작업 요청·상태 조회

외부 수집은 브라우저가 AI 서버에 직접 지시하지 않고 Spring에서 인증한 뒤 내부 작업으로 전달한다. 작업 소유 조직·job ID를 서버에서 지정한다. API 키를 브라우저와 로그에 노출하지 않는다. 재시도는 같은 자료를 중복 생성하지 않으며 오류를 판매 판단으로 변환하지 않는다.

CSV는 1차 후보·공급 입력, 2차 일별 실적 입력 순서로 추가한다. 사용자에게 미리보기와 행별 오류를 보여준 뒤 확정하고, 재업로드는 같은 키에 대한 수정인지 새 행인지 표시한다. MVP에서 임의 URL의 서버 측 자동 다운로드는 하지 않는다.

## 7. 수집원 도입 순서

데이터 구독료 없는 경로를 우선한다. 서버·모델 비용까지 0원이라는 뜻은 아니다. API 키가 없거나 사용 조건이 확인되지 않은 소스는 비활성 상태로 두고 수동 입력으로 진행한다.

| 우선순위 | 수집원 | 도입 범위 / 조건 |
|---|---|---|
| 필수 | 수동 URL·메모·CSV | 소스 승인 없이도 업무 흐름 검증. 사용자가 확보한 정보만 입력 |
| 1차 자동화 | Google Trends 공식 RSS | 새 키워드 발굴. 뉴스성 결과를 상품군 검토로 거름. 응답·필드·이용 조건을 구현 전에 실측 |
| 1차 공급 연계 | 도매매·도매꾹 API | 후보 선택 후 공급 검색. 계정의 요금·한도·위탁 조건 확인 후 활성화 |
| 후속 | YouTube Data API | 선택 카테고리의 영상·원본 지표 참고. 기본 MVP에서 임의 급등 점수 제외; 적용 정책·보관 규칙 확인 |
| 후속 | Kakao 검색·KOTRA 상품DB | 용어 해석·상품군 자료 보강. 먼저 작은 수동 실험의 병목인지 확인 |
| 보류 | Yahoo Japan·라쿠텐 | 일본 트렌드는 참고용. Yahoo 상업적 사용, 라쿠텐 비공개 도구 사용 조건 확인 전 의존 금지 |

국내 판매 채널의 초기 근거는 수동 기록한다. 전체 쇼핑몰 판매량을 무료로 자동 수집할 수 있다고 가정하지 않는다. RSS와 문서 공개는 임의 HTML 대량 수집 허가로 확대 해석하지 않는다.

## 8. 구현 순서와 단계별 완료 기준

기간은 일정 약속이 아닌 1인 개발의 초기 작업일 추정이며, 계정 승인·실제 판매 관측 기간은 별도다. 모든 단계에서 코드 변경에 맞는 검사만 수행한다.

| 단계 | 작업 | 완료 기준 | 예상 |
|---|---|---|---|
| P0 범위·연결 정리 | 완료된 네이버 쇼핑 검색 제거를 기준선으로 확인하고 고정 키워드 비활성 계획, 기존 스키마·권한, 후보 상태와 비용 정의 확정 | 실데이터와 샘플·과거 자료 구분, 기존 화면 접근 유지, 새 경로 권한 정의 | 1~2일 |
| P1 수동 검증 업무 | Flyway 추가, 후보·상품군·공급·채널 근거 CRUD, 비용 계산과 검증 보드 | 외부 API 없이 후보 1건을 READY까지 진행. 미확인 비용은 완료로 표시되지 않음 | 3~5일 |
| P2 판매 실험 | 실험·일별 결과·판정 이력, CSV 실적 입력, 예산·기한 표시 | 실제 판매 기록을 넣어 잠정/확정 결과와 다음 행동을 확인. 첫 파일럿 시작 가능 | 2~4일 |
| P3 필요한 자동화 | Google RSS, 검증된 도매 API, 작업 상태·중복·실패 처리, 수집기 결함 수정 | 수동 입력과 같은 모델에 자료가 들어오고 재실행해도 중복 없음. 키 없는 소스는 다른 흐름을 막지 않음 | 2~4일 |
| P4 파일럿 평가 | 한 상품군·한 채널에서 후보 10개/실험 최대 3개 운영, 병목과 이익 기록 | 모든 실험에 HOLD 포함 판정과 근거가 남음. 수입 후보가 없어도 모듈 사용성 검증 완료 가능 | 관측 2~4주 제안 |

P2가 끝나면 판매 파일럿을 시작하고, P3는 수작업 병목에 맞춰 선택한다. API 수집 완성을 기다리느라 판매 검증을 미루지 않는다. P4의 2~4주는 관측 창이며 그 안에 수익성이 증명된다고 보장하지 않는다.

### 첫 구현 작업 묶음

1. 기존 작업 트리를 보존하고 신규 validation 패키지·화면의 변경 범위 지정.
2. 현재 최신 migration 번호를 확인한 뒤 새 Flyway 파일 추가. 현재 적용 대상인 V01~V18은 수정하지 않으며 다음 후보 번호는 V19다.
3. 후보·상품군·공급 조건·채널 근거·비용 스냅샷부터 구현.
4. 새 경로의 조직 권한과 참조 무결성 검사 추가.
5. `/validation` 보드와 상세 화면을 공통 API 클라이언트로 연결.
6. 가상 예시를 명시한 계산 검증 후 사용자의 실제 후보 1건으로 수동 흐름 점검.

이 작업 묶음에는 신규 외부 API 연결, 수출, 통관 기능을 넣지 않는다.

## 9. 검증 계획과 성공 판단

### 소프트웨어 완료 기준

- 외부 API 키 없이 후보→공급→채널→비용→실험→판정을 끝낼 수 있다.
- 주문당 비용 예시 2,500원, 묶음 수량, 유료·무료 배송, 누락 비용, 환불·미정산을 의미 있는 계산 테스트로 검증한다.
- 다른 조직의 후보·비용·실적 조회/수정 차단, VIEWER 쓰기 차단, CASE 접근 차단을 통합 테스트한다.
- 동일 공급 상품 가격 변경과 수집 재실행, CSV 재업로드 시 중복 및 과거 비용 덮어쓰기가 없다.
- API 403/429·시간 초과·빈 결과를 구분하고 제한된 재시도 후 상태를 남긴다.
- 후보 선택부터 실험 결과·판정까지 주요 사용자 흐름을 한 번 종단 검증한다.
- 기존 인증·조직·선적 기능을 변경한 부분에는 해당 회귀 검사를 수행한다.

### 사업 검증 기준

개발 완료와 상품 수익성 검증은 별개다. 후보 수집량·조회수·기능 개수는 수익성 증거가 아니다.

- 실험 시작 전 기간, 광고 예산, 최대 손실, 목표 주문당 공헌이익을 직접 설정한다. 미설정이면 시작하지 않는다.
- 주문·정산·반품·응대 부담을 확인하고 KEEP/STOP 등을 결정한다. 예산 도달 표시는 운영자에게 중단 판단을 요구하며 외부 채널을 자동 제어하지 않는다.
- 일회성 주문만으로 SCALE 또는 수입 성공을 선언하지 않는다. 서로 다른 관측 기간의 판매 지속성, 공급 안정성과 비용 변화도 본다.
- 데이터 부족은 HOLD로 남기고 ‘추가 노출 확보’처럼 다음 실험을 적는다. 상품군·기간·예산은 결과를 좋게 보이게 하려고 소급 변경하지 않는다.

## 10. 국내 판매 결과를 수입 검토로 넘길 선택 조건

IMPORT_REVIEW는 수입 발주 승인이나 플랫폼 전체의 필수 진입 조건이 아니라, 국내 판매 경로에서 얻은 근거를 후속 수입 조사로 넘기는 선택 표식이다. 이 경로를 사용하는 경우 다음이 준비된 후보부터 검토한다.

1. 국내에서 본인 판매가 발생했고 가격·옵션·채널·기간과 잠정/확정 수익을 설명할 수 있다.
2. 직접 소싱으로 개선하려는 원가·품질·차별성 문제가 명확하다.
3. 해외 공급자와 견적·최소 수량·샘플 조건을 확인할 수 있다.
4. 운송·통관·판매 요건·반품·재고 자금까지 포함해 비교할 수 있다. 미확정 값은 후속 모듈의 확인 과제로 넘긴다.

인계 자료는 상품군·정확한 모델/옵션·판매 근거·국내 공급 조건·비용 버전·목표 개선점·미확정 항목이다. 해외 수요 자료를 국내 판매 증거로 대체하지 않는다. 국내에서 팔린 상품군이라도 수입하는 브랜드·모델이 바뀌면 다시 판매 검증한다.

실제 거래가 결정된 뒤에만 기존 무역 운영 도메인의 PI·품목 라인과 연결한다. 후보의 공급 국가·관측 국가를 실제 원산지로 자동 복사하지 않는다. 이번 구현에서는 인계 요약과 참조 ID만 준비한다.

## 12. 아직 정하지 않은 운영값

첫 상품군, 실제 판매 채널, 판매자 계정 준비 상태, 실험 예산·최대 손실, 목표 공헌이익, 공급 API 계정 조건은 미정이다. 이 값들은 문서 작성이나 수동 입력 기능 개발을 막지 않는다. 실제 판매 실험 시작 전에 채운다.

문서 이후의 첫 개발 목표는 P0~P1의 수동 검증 업무다. 첫 상품군을 고르는 데 필요한 근거부터 저장하고, 사용자가 실제로 시험할 후보를 선택할 수 있는 상태를 만든다.
