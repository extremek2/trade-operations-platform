# 2단계: 조직 개설 신청·이메일 확인·관리자 승인 백엔드

> 역사 기록: 이 문서의 migration 번호는 작성 당시 기준이다. 현재 빈 DB 설치 기준은 ADR-0002의 V1/V2이며 이 절차를 재실행하지 않는다.

- 작성일: 2026-09-08
- 상태: 구현·검증 완료. 화면 통합 결과는 3단계 문서를 따른다.
- 기준 설계: [가입 승인 및 참여 권한](../product/identity-access-approval-design-v1.md)
- 이전 단계: [시스템 권한과 인증 기반](identity-stage-1.md)
- 범위: 백엔드 API·DB·발송 대기 처리. 신청 상태 및 관리자 화면은 3단계다.

## 완료한 업무 흐름

```text
회원가입 → 사용자 + 조직 개설 신청 + 확인 메일 발송 대기 + ACCOUNT 세션
        → PENDING_EMAIL
이메일 링크 확인 POST → PENDING_REVIEW
관리자 승인 → 조직 생성 + OWNER 생성 + APPROVED + 감사 이력 + 알림 발송 대기
관리자 반려 → REJECTED + 사유·내부 메모·감사 이력 + 알림 발송 대기
반려 후 재신청 → 이전 신청을 참조하는 새 신청 생성
```

신청 단계에서는 조직과 OWNER를 만들지 않는다. ACCOUNT 세션은 본인 정보·신청 조회,
신청 제출·이메일 확인 요청·컨텍스트 선택만 가능하다. 기존 화주 조직·OWNER·로그인은 유지한다.
이메일 확인 자체는 로그인하거나 조직 접근 권한을 부여하지 않는다.

관리자 승인 이후에도 기존 ACCOUNT 토큰은 ACCOUNT다. 신청 조회 결과의
approvedOrganizationId로 컨텍스트를 전환하거나 다시 로그인해야 조직 업무에 접근할 수 있다.

## API 계약

모든 경로는 /api/v1 아래에 있다. 기존 ApiResponse envelope를 유지한다.

| 요청 | 인증 및 동작 |
|---|---|
| POST /auth/signup | 계정·신청 생성, ACCOUNT 세션, nextPath=/application 반환 |
| POST /auth/email-verifications/request | 로그인 사용자 본인의 확인 메일 재발급 |
| POST /auth/email-verifications/confirm | 토큰만으로 이메일 확인, 로그인 불필요, 세션 발급 없음 |
| GET /me/applications?page=0&size=20 | 본인 신청 이력만 조회 |
| POST /organization-applications | 기존 계정의 최초 신청 또는 반려 후 재신청 |
| GET /system-admin/applications?status=PENDING_REVIEW&page=0&size=20 | 시스템관리자 검토 목록 |
| GET /system-admin/applications/{id} | 시스템관리자 상세: 신청 정보·내부 메모·처리자 |
| POST /system-admin/applications/{id}/approve | 시스템관리자의 승인 |
| POST /system-admin/applications/{id}/reject | 시스템관리자의 반려 |

목록 크기는 최대 100건이다. status 생략 시 관리자는 모든 상태를 조회한다.
신청자 응답에는 내부 메모와 다른 신청자의 데이터가 포함되지 않는다.

가입 입력 필드는 기존 organizationName, businessNumber, name, email, password, phone을 유지한다.
AuthResponse에는 nextPath를 추가했고 user에는 emailVerified를 추가했다.
조직 없는 신규 가입 응답의 organizationId·organizationName·role은 null이다.
확인 토큰이나 발송 본문은 API 응답에 포함하지 않는다.

이메일 확인 요청 본문:

```json
{"token":"이메일 링크에 포함된 43자 인증 토큰"}
```

승인·반려 요청 본문:

```json
{"version":1,"reason":"신청 정보 확인 완료","internalNote":"운영자 내부 검토 메모"}
```

version은 상세 조회의 최신 값을 사용한다. 이메일 확인도 신청 버전을 증가시킨다.
reason은 신청자에게 공개되는 필수 사유, internalNote는 관리자 전용 선택 메모다.

재신청 본문:

```json
{"organizationName":"보완된 회사명","businessNumber":"사업자 식별정보","phone":"연락처","previousApplicationId":"가장 최근 반려 신청의 UUID"}
```

기존 신청을 수정하거나 덮어쓰는 API는 제공하지 않는다. 동일 사용자의 미처리 신청은
하나만 허용한다. 이미 조직을 소유하거나 승인된 개설 신청이 있으면 추가 개설은 제한한다.
다른 사용자의 이전 신청을 참조하거나 오래된 반려 신청에서 중복 재신청할 수 없다.

실패 응답: 잘못된 확인 링크·형식 400, 인증 실패 401, 권한 부족 403, 없는 신청 404,
중복·상태·버전 충돌 409, 요청 제한 429, 메일 암호화 설정 미비 503.
기존 POST /organizations 직접 생성 경로는 계속 차단되며 직접 생성 서비스도 제거했다.

## 트랜잭션과 동시 처리

- 신청·이메일 확인·결정은 신청자 행을 먼저 잠근다. 결정 시 그다음 신청 행을 잠근다.
- 신청 상태·version·이메일 확인 여부·신청자 활성 상태를 다시 검사한다.
- 승인 시 조직·OWNER·신청 변경·감사·메일 대기 저장이 모두 함께 커밋된다.
- 동시에 승인하거나 승인·반려가 경쟁해도 하나만 성공한다. 실패한 요청은 409로 응답한다.
- 실제 SMTP 실패는 이미 커밋된 승인을 되돌리지 않는다. DB 발송 대기 저장 자체가 실패하면
  승인 트랜잭션 전체를 롤백한다.
- 이메일 인증 토큰 소비는 미사용·미철회·미만료·대상 이메일 일치 조건의 원자적 UPDATE다.
- 감사에는 신청 제출·이메일 확인·승인·반려를 남긴다. 개인정보가 있는 제출본은 신청 테이블에
  보존하고 감사 값에는 상태 전이를 기록한다.

## 이메일 확인과 발송

확인 토큰은 난수 32바이트이며 URL-safe Base64 43자로 표현한다. 검증 테이블에는 해시만 저장한다.
발송 전 원문 토큰을 다시 사용할 필요가 있으므로 메일 본문은 별도 outbox에 AES-256-GCM으로
암호화하여 보관한다. 비밀키는 DB나 소스에 저장하지 않는다.

확인 링크는 설정된 고정 프런트 주소에 #token=... 형식으로 붙인다. 요청의 Host 헤더로
링크를 만들지 않는다. HTTPS를 요구하며 localhost 개발 주소만 HTTP를 허용한다.
GET으로 확인이 완료되지 않으며, 3단계 화면에서 사용자의 확인 후 POST로 토큰을 소비한다.
프런트 주소에는 인증 토큰을 서버 접근 로그에 남기는 query string을 사용하지 않는다.

기본 제한:

- 토큰 유효기간: 15분.
- 본인 확인 메일 재발급: 1분에 1회, 1시간에 최대 5회. 최초 발급도 포함한다.
- 재발급 시 기존 미사용 토큰은 철회하고 미발송 본문은 삭제한다.
- 공개 가입·확인 요청: 각각 원격 주소별 분당 30회. 카운터는 별도 DB 트랜잭션에 남겨
  인증 실패 롤백으로 초기화되지 않게 한다.
- 프록시가 있는 운영 환경에서는 신뢰할 프록시 범위와 클라이언트 IP 전달 설정을 별도 적용한다.
  클라이언트가 보낸 임의 X-Forwarded-For를 직접 신뢰하지 않는다.

MailTransport 인터페이스로 발송 구현을 분리했다. 테스트는 대역을 사용하고 실제 SMTP는
명시적으로 활성화해야 동작한다. 워커는 커밋된 outbox를 FOR UPDATE SKIP LOCKED로 한 건씩
가져와 처리한다. 네트워크 작업 동안 해당 행의 잠금을 유지하므로 SMTP 연결·읽기·쓰기 제한은
각각 5초를 기본값으로 둔다.

발송 실패 시 1분 후 재시도하고 총 5회 실패하면 FAILED로 종료한다. 성공·만료·취소·최종 실패 시
암호문 본문을 삭제한다. 제공자 오류 메시지는 토큰을 포함할 수 있으므로 저장하지 않고 고정된
DELIVERY_FAILED 코드만 기록한다. 승인·반려 알림은 7일 동안 발송을 시도하며 내부 메모를 포함하지 않는다.

DB와 SMTP를 한 번의 원자적 커밋으로 묶을 수 없으므로, 전송 직후 DB 커밋 전에 장애가 발생하면
메일이 중복 발송될 수 있다. 안정적인 outbox UUID를 X-Trade-Ops-Message-Id 헤더에 넣지만
메일 제공자의 중복 제거를 보장하지 않는다. 인증 토큰의 일회성은 DB에서 별도로 보장한다.

## 설정과 미적용 항목

| 설정 | 용도 및 기본값 |
|---|---|
| MAIL_OUTBOX_KEY | Base64로 인코딩한 무작위 32바이트 키. 기본값 없음 |
| MAIL_DISPATCH_ENABLED | 실제 발송 스케줄 활성화. 기본 false |
| MAIL_FROM | 발신 주소. 발송 활성화 시 필수 |
| MAIL_VERIFICATION_URL | 확인 화면 주소. 기본 http://localhost:3000/verify-email |
| SPRING_MAIL_HOST / PORT / USERNAME / PASSWORD | SMTP 제공자 설정 |
| spring.mail.properties.mail.smtp.* | 운영 제공자에 맞는 인증·TLS·연결 제한 설정 |

MAIL_OUTBOX_KEY가 없으면 기존 로그인은 가능하지만 메일 저장이 필요한 신규 가입·재발급·결정은
503으로 실패하고 부분 변경은 롤백된다. 운영 환경에서는 키를 먼저 안전하게 설정해야 한다.
테스트 키는 테스트 설정에만 존재하며 운영 키로 사용하지 않는다. 키 교체 전에는 이전 키로
암호화된 미발송 항목을 처리하거나 취소해야 한다.

발송을 비활성화하면 외부 이메일은 보내지 않는다. 만료 데이터 정리도 dispatcher 실행 시
처리하므로, 장기간 발송 중단 시 별도의 만료 정리 실행이 필요하다. 삭제 작업은 운영 승인 후
진행하며, 이 단계에서 운영 데이터를 삭제하거나 서비스를 실행하지 않았다.

2단계 완료 당시에는 신청 상태·이메일 확인·관리자 승인 화면이 없었다.
이후 [3단계](identity-stage-3.md)에서 nextPath와 ACCOUNT 흐름 및 승인 화면을 구현하고
통합 검증했다. 초기 관리자 실제 생성, 메일 제공자 연결, 실제 이메일 발송과 배포는 수행하지 않았다.

## DB 전환

새 V15 마이그레이션으로 신청, 확인 토큰, 메일 outbox, 요청 제한 테이블과 email_verified_at을
추가했다. V01~V14는 수정하지 않았다. 기존 조직·OWNER의 재승인이나 이메일 확인 강제는 하지 않는다.

이메일은 trim 및 소문자화하고 함수형 UNIQUE 인덱스를 적용한다. 정규화 결과가 같은 기존
계정이 발견되면 마이그레이션을 중단한다. 계정을 임의로 합치거나 삭제하지 않는다.
사업자번호 중복만으로 조직 소유권을 자동 인정하지 않으며 승인자가 별도 검토해야 한다.

## 검증 결과

- 격리된 PostgreSQL에서 백엔드 전체 테스트 49개 통과.
- bootJar 빌드 성공. SMTP 시간 제한 기본값 추가 후 서버 기동 테스트와 빌드도 재확인했다.
- 신규 가입의 조직 권한 차단, 기존 화주 인증, 승인 후 컨텍스트 전환 검증.
- 동시에 승인·반려하거나 인증 토큰을 소비하는 상황 검증.
- 반려 후 스냅샷 보존, 본인 신청 격리, 관리자 내부 메모 비공개 검증.
- 가입 및 승인 중 발송 대기 저장 실패 시 전체 롤백 검증.
- 토큰 만료·철회·재사용·대상 이메일 불일치·요청 제한 검증.
- 메일 암호화·실패 재시도·성공·만료·최종 실패 시 본문 삭제 검증.
- git diff --check 통과. 프런트엔드는 이 단계에서 변경하지 않았다.

테스트 명령은 api-server에서 ./gradlew test bootJar이며 Docker가 필요하다.
실제 서비스 DB는 사용하지 않는다. 후속 화면 구현 결과는 [3단계 문서](identity-stage-3.md)에 기록한다.
