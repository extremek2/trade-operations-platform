- 상태: 구현·검증 완료
- 기준: [가입 승인 및 참여 권한 설계](../product/identity-access-approval-design-v1.md)

## 사용자 흐름

화주 OWNER·ADMIN은 화물 상세의 **외부 업체와 담당자** 영역에서 포워더·관세사 업체를
등록하고 해당 건에 연결한다. 업체 등록 자체에는 접속 권한이 없다. 같은 업체는 다른 건에도
연결할 수 있지만 담당자 초대와 권한은 건마다 별도로 지정한다.

업체를 연결한 뒤 담당자 이름·이메일·권한을 입력하고 최종 확인하면 초대와 메일 발송 대기가
같은 트랜잭션으로 저장된다. 이 건의 업체별 초대 대기·참여 중 인원 합계는 최대 3명이다.
철회·만료된 초대는 정원에 포함하지 않는다. 3명 제한은 UI뿐 아니라 서버 잠금 안에서도 검사한다.

담당자는 메일 링크를 열고 **초대 확인하고 건에 접속** 버튼을 눌러 참여한다. 외부 담당자가
신규 사용자라면 비밀번호 없는 공통 사용자 계정만 생성한다. 화주 직원 소속이나 조직은
생성하지 않는다. 기존 계정이면 같은 사용자 ID를 사용하며 비밀번호·소속·기존 역할은 유지한다.
해당 링크로 발급하는 세션에는 초대받은 건의 권한만 부여한다.

| 참여 권한 | 허용 기능 |
|---|---|
| VIEWER | 해당 건의 운송 정보와 운송 문서번호 조회 |
| CONTRIBUTOR | 조회 및 운송 문서번호 추가 |

포워더와 관세사에 동일한 두 접근 수준을 제공한다. 화물 전체 변경·보관, 대표 운송 문서 지정,
조직 직원 관리, 다른 건 조회, 외부 재초대와 최종 통관 승인은 허용하지 않는다.
외부 화면에는 화주 참조번호·구매주문번호·다른 참여자의 연락처를 제공하지 않는다.
현재 파일 첨부·다운로드 기능은 이 외부 API에 연결하지 않는다.

## 화면·API

| 화면 | 용도 |
|---|---|
| `/shipments/{shipmentId}` | OWNER·ADMIN의 업체 연결·담당자 초대·철회 |
| `/external-access` | 초대 확인, 만료된 접속 링크 재요청 |
| `/external-case` | 현재 초대받은 건 조회·허용된 문서번호 등록 |

| API | 권한 |
|---|---|
| `GET/POST /api/v1/organizations/current/partners` | OWNER·ADMIN: 업체 목록·등록 |
| `GET/POST /api/v1/shipments/{id}/partners` | OWNER·ADMIN: 건별 업체 목록·연결 |
| `POST /api/v1/shipments/{id}/partners/{partnerId}/invitations` | OWNER·ADMIN: 이메일 초대 |
| `POST /api/v1/shipments/{id}/participants/{participantId}/revoke` | OWNER·ADMIN: 사유를 남기고 철회 |
| `POST /api/v1/auth/case-links/request` | 초대 ID·대상 이메일로 새 접속 링크 요청 |
| `POST /api/v1/auth/case-links/confirm` | 미사용 이메일 토큰 확인·소비, CASE 세션 발급 |
| `GET /api/v1/case-workspace/{shipmentId}` | 현재 CASE 세션의 해당 건만 조회 |
| `POST /api/v1/case-workspace/{shipmentId}/documents` | 해당 건 CONTRIBUTOR만 문서번호 추가 |

SYSTEM_ADMIN의 PLATFORM 세션이나 OPERATOR·VIEWER 조직 세션에는 초대 관리 권한이 없다.
외부 세션은 기존 `/shipments` API와 조직 관리 API에 접근할 수 없다.
CASE 컨텍스트는 일반 컨텍스트 전환 API에서 직접 선택할 수 없으며 이메일 확인으로만 발급한다.

## 링크 수명·메일·세션

- 최초 초대 수락 기한은 기본 7일, 개별 접속 토큰은 기본 15분이다.
- 최초 수락 후에는 참여가 철회되기 전까지 같은 초대 페이지에서 새 접속 링크를 요청할 수 있다.
  최초 7일 기한은 이미 수락한 참여의 종료일이 아니다.
- 링크는 `#invitation=<공개 초대 UUID>&token=<난수>` 형식이다. 공개 초대 ID만으로
  접속할 수 없고 대상 이메일로 받은 짧은 수명의 토큰이 필요하다.
- 화면은 fragment를 읽고 주소에서 제거한다. GET으로 접속·수락되지 않으며 명시적인 POST가
  필요하다. 토큰은 브라우저 저장소에 보관하지 않는다. 새로고침·로그아웃 후에는 원래 메일을 다시 연다.
- 새 접속 링크를 발급하면 이전 미사용 토큰과 미발송 메일을 취소한다. 요청 제한은 초대별
  1분 1회·1시간 5회, 공개 링크 요청·확인은 IP별 1분 합계 30회다.
- 알 수 없거나 철회·만료된 초대의 재요청은 일반 안내로 응답한다. 실제 접속에서는 항상
  초대·토큰·대상 이메일·사용자 활성 상태·소유 조직·건 상태를 다시 검사한다.
- 다른 계정으로 로그인 중이어도 확인한 초대 이메일의 계정으로 브라우저 접속이 전환됨을
  버튼 전에 안내한다. 확인 요청에는 기존 Authorization 헤더를 보내지 않는다.
- CASE 세션은 참여 ID를 참조하며 모든 보호 요청과 refresh에서 최신 참여 상태를 확인한다.
  한 이메일의 여러 건 세션은 분리된다. 한 건에서 철회해도 다른 건의 참여는 유지된다.
- 철회는 초대, 미사용 토큰, 발송 대기, 해당 참여의 세션을 함께 차단한다. 재초대해도 이전
  링크와 세션은 복구되지 않는다. 보관된 건이나 비활성 조직·계정에도 접근할 수 없다.

설정은 다음 환경변수로 지정한다.

| 설정 | 기본값 |
|---|---|
| `MAIL_CASE_ACCESS_URL` | `http://localhost:3000/external-access` |
| `CASE_INVITATION_DAYS` | `7` |
| `CASE_LOGIN_MINUTES` | `15` |

운영 링크 주소는 query·fragment 없는 HTTPS 주소여야 한다. localhost HTTP만 개발용으로
허용한다. `MAIL_OUTBOX_KEY`, 메일 제공자 설정과 `MAIL_DISPATCH_ENABLED`는
[2단계 메일 설정](identity-stage-2.md)을 따른다. 화면의 초대 성공은 발송 대기 저장 완료를
뜻하며 실제 이메일 수신 완료를 뜻하지 않는다.

## 데이터 전환·동시 처리·감사

V17에서 `partner_company`, `case_partner`를 추가하고 기존 연락처·참여·초대 테이블과
연결했다. `email_auth_token`에는 CASE_LOGIN 목적과 초대 참조를 추가하고
`refresh_session`에는 CASE 목적·참여 참조를 추가한다. 기존 V01~V16은 수정하지 않는다.

조직·건·업체 잠금 아래 정원과 중복을 검사한다. 초대 수락 시 사용자 이메일을 다시 확인하고
토큰의 미사용·미철회·미만료 조건을 원자적으로 갱신한다. 활성 참여는 동일 건·사용자 중복을
DB 인덱스로도 차단한다. 업체 등록, 건 연결, 초대, 링크 확인, 철회와 외부 문서번호 등록을
감사 이력에 기록한다. 초대·메일 저장 실패 시 연락처와 참여 생성도 함께 롤백된다.

기존 연락처 회사명을 기준으로 업체를 자동 병합하지 않는다. 기존 미분류 연락처와 EDITOR
참여는 보존하며 CASE 세션 대상으로 자동 전환하지 않는다. 기존 연락처 이메일이 충돌하면
임의로 매핑하지 않고 명시적인 데이터 정리를 요구한다. 같은 화주 조직에서 한 이메일은
하나의 연락처 업체에 속하도록 한다. 같은 연락처는 여러 건에 초대할 수 있다.

이번 단계에는 업체 전체 업무를 보는 포워더·관세사 조직 화면이 없다. 업체 ID와 건별 연결을
분리해 향후 업체 조직을 연결할 여지를 두었다. 향후 연결만으로 기존 건 권한이 확대되어서는 안 된다.
담당자 접근 수준을 바꾸려면 현재 참여를 철회하고 새 수준으로 재초대한다.

## 검증 결과

- 백엔드 전체 81개 통과. 외부 참여 통합 테스트 17개와 기존 협업 데이터 전환 테스트 1개 추가.
- 프런트엔드 전체 31개 통과. 건별 라우팅, 링크 명시 확인·주소 제거·같은 페이지에서 재열기,
  만료 재요청, 세션 철회, 3명 제한, 최종 확인·중복 클릭, 문서번호 등록 검증.
- 실제 Chrome E2E 4개 통과. 기존 가입 승인·반려·직원 관리 3개와 외부 업체별 3명 초대→
  이메일 접속→문서번호 등록→철회·기존 링크 차단 1개.
- 동시 초대 시 정원 초과 방지, 동시 토큰 소비 1회 성공, 초대·토큰 만료와 재발급,
  다른 건 접근 차단, 한 이메일의 여러 건 참여·철회 분리, 발송 저장 실패 롤백 검증.
- 프런트엔드 프로덕션 빌드와 백엔드 bootJar 성공. 운영 JAR에 V17이 포함되고 테스트 서버가
  포함되지 않음을 확인했다. 모바일 외부 참여 화면과 가로 넘침도 확인했다.
- `git diff --check`와 문서 상대 링크 검사 통과.

실행은 `api-server`에서 `./gradlew test bootJar --no-daemon`, `frontend`에서
`CI=true npm test -- --watchAll=false --runInBand`, `CI=true npm run build`, `npm run test:e2e`다.
테스트 환경과 격리 방식은 [3단계 실행 안내](identity-stage-3.md)를 따른다.

## 운영 적용과 다음 단계

실제 서비스 DB 변경, 실제 외부 담당자 초대 메일 발송과 배포는 수행하지 않았다.
브라우저 테스트는 격리된 PostgreSQL과 메모리 메일함을 사용한다.
후속 [6단계 운영 준비](identity-stage-6.md)에서 운영 설정·메일 검증·기존 데이터 전환 및
복구 절차를 준비했다. 실제 환경 정보 확정과 실제 계정 생성·발송·배포는 아직 수행하지 않았다.
